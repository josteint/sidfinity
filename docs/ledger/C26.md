### C26 — Song data ABSENT from the file image (init GENERATES/unpacks it in RAM)

- **Problem shape:** the player is a known variant (canon/2entry body matches),
  its data-table operands are internally CONSISTENT — but they point OUTSIDE
  the loaded image (or at zero fill): the member's init generates or unpacks
  the song data into high RAM at runtime. Any file-image extraction reads
  nothing. Seen as `nonstandard_instr_base` refusals (DMC family-1 Flash trio:
  instr $B961/$A70B/$ACEA, ALL six table operands out of image) and, composed
  with a banking wrapper, `nonstandard_vectors` (Itinerant: init copies
  $1900→$7100 behind `LDA #$35/STA $01`).
- **Canonical fix:** read what the ENGINE reads — run the member's OWN init
  under py65 and extract every data table + priming byte from the POST-INIT
  RAM (`DMCV4Config.data_post_init` → extract swaps its whole memory for
  `_postinit_window(s, 0, 0x10000)`). Detection signature is all-or-nothing:
  EVERY data operand outside the image ⇒ unpacker (a mixed layout stays
  refused). Skip the canonical packing-order (layout) check for this class —
  the unpacked tables sit wherever the unpacker put them. Verify-gated; both
  acceptance paths run only where the extractor previously refused, so FULL
  regressions are impossible by construction.
- **⚠ THE OPERAND COUNT IS A PROXY; THE CLAIM IS "THE INIT WROTE IT" — MEASURE
  IT (2nd occurrence, DMC v5 2026-08-27).** "EVERY operand outside the image"
  is not the C26 hypothesis, it is a cheap stand-in for it, and it has a
  systematic false-negative: tables that live INSIDE THE PLAYER BODY are
  in-image by construction and never move. `Piirainen_Antti/
  Left_Ear_Bleedin_Ear_Left` is a genuine unpacker (init pastes the song to
  $4000-$4700/$6000+) whose 3 in-image operands are the two freq tables (in
  the player, they relocate with the base) and the sector-LO table (a zero
  block in the player tail — every sector page-aligned ⇒ every low byte $00).
  All-or-nothing refused it for years. TEST THE HYPOTHESIS DIRECTLY: snapshot
  RAM before init (power-on pattern + psiddrv's $0000-$03FF wipe + the image)
  and after, and require every OFF-IMAGE table address to differ. That is
  decidable from two snapshots, needs no new machinery, and is what separates
  an unpacker from a MISIDENTIFIED player — whose "table operands" are not
  addresses at all and which writes none of them (`Ed/We_Were_All_Kids` reads
  a `STA` opcode byte plus its operand low byte as "orderlist $D89D").
- **⚠ SNAPSHOT AT THE PLAYER LANDING, NOT AT INIT'S END, when the init reaches
  one.** The landing is the exact analogue of the file image an ordinary
  in-image member is extracted from: post-unpack, but before the player's own
  init overwrites the leftover state the extract reads as PRIMING (the
  `_postinit_window` docstring's own warning). Fall back to a completed init
  for an unpacker that never lands on a player head, and REFUSE when py65
  cannot run the init at all — never silently fall back to the empty image.
- **⚠ ONE DEFINITION OF THE GATE.** The probe must consider exactly the members
  the refusal would otherwise kill. Two copies of the condition drift, and the
  drift is invisible in both directions: a probe stricter than the refusal
  misses carriers, a looser one pays a py65 run for the whole family. Factor
  it (v5: `factory.data_tables_off_image`, called by both).
- **Related prior forms (same principle, narrower scope):** `_postinit_window`
  on the filter defs (Ed members' init stamps res/cutoff over the records),
  `post_init_state` priming capture (dataflow members whose init clears
  leftovers), round-40 filter_mod contour (init-generated triangle table).
  This entry is the WHOLESALE form: all tables at once.
- **Banking-wrapper base candidate (C13 tier, same session):** a play vector
  `LDA #$35/STA $01/JSR t/LDA #$37/STA $01/RTS` whose jump table was
  overwritten by the wrapper/init code names the play handler explicitly:
  base = t−$50 (2entry) / t−$85 (canonical), validated by the masked identity
  compare downstream.
- **Status:** recurring (2× wholesale — DMC v4 Flash trio + Itinerant; DMC v5
  Left_Ear_Bleedin_Ear_Left via the measured gate. Narrower forms 3× prior).
  Per-occurrence status in [[project_dmc]]. The two wholesale implementations
  (`DMCV4Config.data_post_init` counted; `DMCV5Config.data_post_init`
  measured) are a factor-candidate — converge on the MEASURED one.
