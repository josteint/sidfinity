### C38 — song-end master-vol FADE → silence → whole-song RESTART loop (appended play-vector wrapper) with a measured survivor prime

**Problem class.** A member appends a routine to the PLAY vector that implements
a song-end fade-out/restart loop entirely at play() level (no init involvement
until the restart):

1. **Trigger** — count play() invocations to N.
2. **Ramp** — from play N, `dec` the master-volume shadow by 1 every STEP plays.
   The value is emitted for free by the existing note-init `ora mvol / sta $D418`
   filter-tail write — the wrapper never writes $D418 itself during the fade.
3. **Silence** — once mvol hits 0, write `$D418 = $00` (and run NO play body) for
   SIL plays.
4. **Restart** — `JMP` a re-init that resets the counters and restarts the WHOLE
   song, looping forever.

The restart re-runs the engine's SHARED init path — the SAME code a cold start
runs — which clears the effect/state block (`$1718-$179D`: pulse accumulator,
pending flag, filter/vibrato/glide, the ACTIVE pulse-record offset `$174D`, …)
but LEAVES the note-state block `$100F-$1018` untouched. So the replay resumes
its first notes from the END-OF-SONG survivor note-state, not from a clean cold
state.

**How it presents.** The member verifies FULL through the entire first play, the
fade ramp, and the silence, then diverges DEEP in the REPLAY (~98% of the
stream). The fade `$D418` values and the `$00` silence run match; the divergence
is in a REPLAYED note whose behaviour depends on the survivor note-state. A
composer that reproduces the loop but primes the survivors slightly wrong
diverges on exactly the write the wrong survivor drives.

**Canonical solution.**

*Detect* with a STATIC gate (C19-style opcode probe, never a stream scan): the
fade decrement `DEC ctr / LDA ctr / STA <mvol_shadow>` plus a `LDA #$00 / STA
$D418` silence write in the appended region. Relocation-aware (compute the
counter/shadow addresses from the player base).

*Measure* the fade schedule AND the survivor note-state from libsidplayfp
(siddump native-capture) — **NEVER py65**: every one of these values feeds the
SID write stream, so [[feedback_ground_truth]]'s third failure mode forbids a
py65 read (the deep-playback state a restart resumes is emulator-dependent).

- **N, STEP** — `--pc-watch` the fade decrement's STA PC; the first hit's
  play-invocation index is N, the delta between the first two is STEP.
- **SIL** — the longest contiguous run of `$D418 = $00` writes in the writelog
  (the only `$00` run: init/normal $D418 is `$0F`/`$1F`, fade values are
  mid-range).
- **Survivor note-state** — `--memwatch-on-write d418 <$100F-$1018>`, taking the
  mode over the silence-phase (`$D418 = $00`) snapshots (the block is frozen
  there — no play body runs).

*Compose* a MODULAR play-vector wrapper — the four phases as independent pieces
and the restart as a separate reusable `songrestart` module reached by JMP:
count-to-N → `dec mvol` ramp (the note-init emits the faded $D418) → `$D418=$00`
silence → `songrestart` = reset the play counter, `jsr init` (cold clear), then
PRIME the survivors. Keep the fade counters OUTSIDE the composer's cleared state
block so `init` cannot wipe the play counter.

**⚠ Prime EXACTLY the init-uncleared survivor block, and nothing more.** The
survivors are `$100F-$1018` = gatemask (`$100F`), curnote (`$1012`), curinst
(`$1015` — the STICKY instrument NUMBER) and shadow17 (`$1018`). Do **not** also
prime the ACTIVE pulse-record cache `cinst` (the composer's mirror of the orig's
`$174D` record offset): `$174D` lives in `$1718-$179D`, which init CLEARS to 0.
A voice whose first REPLAYED note is SOFT (a glide — it takes the running-effects
path and never note-inits, so it never copies `curinst → cinst`) then runs
`fx_pulse` against the survivor instrument's pulse program instead of instrument
0, sweeping PW where the orig (cinst-offset 0) holds it flat. Symptom: PW-lo
alternating (e.g. `$40/$00` from a bounce) across a glide note whose freq
trajectory otherwise matches perfectly. Cure: prime `curinst` only; `jsr init`
already zeroed `cinst`.

The lesson generalises past this member: when reproducing a survivor-preserving
re-init, the survivor set is EXACTLY the init-uncleared address range — measure
which bytes init clears vs leaves, and prime only the leftovers. Priming a byte
init clears (because it happens to share a name/value with a real survivor) is an
over-restore that only bites voices which don't re-derive it.

**Boundary / relations.**

- The FADE is a C10 parametric master-vol contour — a specific mechanism
  (play-counter-driven ramp riding the filter-tail $D418 write), reproduced as a
  named param, NOT decomposed to a `global_track` event list (C10's anti-pattern).
- The RESTART is the sibling of C37 (survivor-preserving re-init): both re-run an
  init that leaves `$100F-$1018` and reproduce it by cold-init + measured prime.
  DISTINCT from C37 in trigger and scope — C37 is a per-SUBTUNE state-copy wrapper
  giving N entry states for one song; C38 is a WHOLE-SONG loop triggered by a
  play() counter (one song, infinitely restarting). DISTINCT from C19 (a static
  single-value poke — here the poke set is the whole survivor block, measured).
- Byte-for-byte the wrapper counter must live outside the init-cleared state so
  the play counter survives the restart's `jsr init`.

**Consumers / status.** logged. First carriers: 4 DMC family-1 members
(Slayer: My_49th_Tune, Plantation, Trip, Worktunes/My_47th_Tune) — all FULL.
Per-occurrence status (rounds r155-157, member list, the Trip cinst refinement)
lives in [[project_dmc]].

- **SIBLING FORM — song-end REST before the repeat, no fade, silence by NOT
  PLAYING (2026-08-14, SLC/Sidewinder/Crazy_Labyrinth, FULL 4/4).** Same
  family as the fade+restart above, three differences: (a) no ramp — the
  tune stops dead; (b) the silence is achieved by NOT CALLING the player at
  all (the chip holds its last state) rather than by writing `$D418=$00`;
  (c) the phases are in the OPPOSITE order — RESTART first, then the rest,
  then play resumes. Mechanism: the play vector is an SMC'd `JMP` that the
  init points at phase 1; phase 1 calls the player then, on ONE subtune,
  compares all three voices' curnote against a sentinel the composer parked
  in each voice's final pattern, and on a match re-inits and re-points the
  JMP at phase 2, which counts down doing nothing.
  ⚠ **DO NOT store the sentinel, and do NOT store the survivors.** Both are
  available and both are the wrong answer:
  * the sentinel is INAUDIBLE (measured: all three voices gated off, the
    note never sounds — for two of them the restart pre-empts the gate-on)
    and its pitch is not even in the pattern data for two voices (it is the
    note AFTER transposition). It is a mechanism byte wearing a pitch's
    clothes — Principle §7. What the sentinel MARKS is already structural:
    each voice's LAST orderlist entry is a dedicated terminator pattern
    (`C-4` + three rests, identical shape on all three voices). So the
    composer triggers on "every voice has entered its final orderlist
    entry", detected at runtime by peeking whether the next track byte is
    the loop terminator — no offsets, no tables, no stored pitch.
  * the survivors (the 10 bytes this entry's fade form MEASURES and stores)
    are saved and restored around the restart instead — the C31 medley
    carry pattern, "self-consistent, no measured constant". THE FADE FORM
    ABOVE SHOULD PROBABLY BE CONVERTED THE SAME WAY (4 Slayer carriers:
    My_47th_Tune / Trip / My_49th_Tune / Plantation); not done here because
    they are FULL and it needs its own round + re-verify.
  REPRESENTATION: one typed field, `MusicSubtune.song_restart_gap` = the
  rest in play() calls. Reads as "this subtune ends, rests N, and repeats".
  The rest length is MEASURED from libsidplayfp (the counter seeds say 255,
  the truth is 256 — never derive it).
  PROBE: static gate (the SMC play-JMP countdown) then a measurement; the
  rest must be IMMEDIATELY PRECEDED BY THE INIT'S ascending clear sweep,
  or an ordinary musical silence reads as a song end (measured: it armed a
  sibling subtune and regressed it from FULL).
  ⚠ ARM PER SUBTUNE. The composer's first cut armed the wrapper globally
  and regressed subtune 0 even with a correct probe — the wrapper checks a
  per-subtune arm table before testing the end condition. A multi-subtune
  member is its own control group; a single-subtune one would have hidden
  both bugs.
  ✅ **THE FADE FORM WAS CONVERTED TOO (2026-08-15, owner-directed).** All
  four Slayer carriers (My_47th_Tune / Trip / My_49th_Tune / Plantation)
  now SAVE/RESTORE the survivor block around the restart instead of
  carrying ten measured bytes in `master_vol_fade`. The params string is
  the SCHEDULE only (`N:STEP:SIL`); the probe no longer measures the
  note-state at all (one fewer siddump run per carrier). A 4th ':' field is
  still ACCEPTED AND IGNORED so stored files written before this still
  build — verified against the on-disk 4-field form. All four re-verify
  FULL, non-carriers byte-identical. The entry's original argument for
  measuring them ("the canon init leaves $100F-$1018 uncleared") still
  explains WHY the block matters; it just never needed to leave the engine.
