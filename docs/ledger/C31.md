### C31 — Compilation: one file packs N INDEPENDENT players, a per-subtune dispatch wrapper selects (player, song)
- **First sight (2026-07-10, DMC v4 family-1, Abyssal_Karma-Part_One, Richard
  Bayliss):** the PSID header overstates songs (5), but the file is a
  COMPILATION of TWO independent, fully-relocated copies of the SAME DMC v4
  engine, each with its own data pool (instruments / freq-wave-filter tables /
  sectors / tracks / tune records). A small SMC dispatch wrapper at the PSID
  init/play vectors maps subtune → (player_base, song): `LDX subtune;
  LDA base_hi_tab,X → STA <both JMP hi-bytes>; LDA song_tab,X → A; JMP
  player`. Here subtune 0 → (player@$8000, song 0); subtunes 1-4 →
  (player@$9100, songs 0-3). Player A carries only 1 real song; player B carries
  4.
- **How it PRESENTS / why the extractor gets it wrong:** `_build_via_canon` base
  detection tries play-3 then LOAD; both players have a valid canonical DMC
  jump table (`4C b+1D 4C b+85`), and the running player is neither play-3 (=the
  wrapper) nor uniquely load — the LOAD-address player (A) wins, and all 5
  subtunes are decoded from A's tune table. sub0 is FULL (it genuinely IS
  player A song 0); subtunes 1-4 read PAST player A's 1-record tune table into
  garbage bytes (tracks point at `$FE` stops or out-of-image $3Cxx) → they
  decode to silence / off-image residue and diverge at frame 1. The downstream
  masked-identity compare does NOT catch it — player A is a byte-valid player,
  just the wrong one for those subtunes.
- **Detection signature:** the file image contains ≥2 canonical DMC jump tables
  at different bases (`4C b+1D 4C b+85`). Bayliss folder alone: 15 such members
  (Balloonacy = 4 players, Lane_Crazy = 4, Defuzion_3 = 3, …); the pattern
  spans the DMC corpus. The dispatch wrapper is the confirmer (per-subtune SMC
  patch of a JMP hi-byte + song# from `LDA tab,X`).
- **Analogues (same class, other engines):** FC Adrenalin ([[project_adrenalin]]
  — "a COMPILATION, 3 engines + 4 independent data pools") and the 5-Title-Tunes
  unified engine ([[project_five_title_tunes]] — multiple independent songs
  merged into one engine via globally-renumbered instruments + per-subtune
  params). DISTINCT from C27/C28 multi-SID: those are N players running in
  PARALLEL on N chips every frame (merged chip-tagged stream); a compilation
  runs exactly ONE player per subtune, SEQUENTIALLY selected — the per-subtune
  streams are fully independent.
- **Canonical solution — UNIFIED-MERGE (built 2026-07-10, `pipelines/dmc/v4/
  compilation.py`):** the 5TT playbook, extract-side only, NO USF/composer
  change. `detect_compilation` (>=2 canonical JT bases + static wrapper decode
  of the base-hi + song X-indexed tables) -> per-subtune (player, song) map;
  `factory.dmc_v4_config(base_override=B)` extracts each player as a standalone
  canonical DMC (canon path for a UNIFORM relocation; on its code-identity
  mismatch, the signature-based `_build_via_dataflow(base_override)` handles the
  NON-uniformly-relocated players — the packer moves state scratch, e.g. the
  $100C active-flag array, independently of the code); `merge_models` merges
  into one DmcModel — shared freq/vibdepth (verified identical), instruments
  renumbered+deduped into one compact <=28 pool, songs reordered by PSID
  subtune, rows' instr rewritten. Then the ordinary `model_to_usf` -> composer
  (compilation-unaware). Two knobs made it work: (i) mask the all-off/sfx
  jump-table entries ($1006-$100B) in the canon compare for base_override
  players — packers point them at a SHARED all-off routine, write-stream-
  irrelevant; (ii) FILTER-DEF window: strategy-1 SHARE the start player's
  17-record window when non-start players' played defs coincide (Abyssal_Karma);
  strategy-2 COMPACT-remap+dedup on conflict, gated on no played def OVERRUNNING
  (C2 repeat<=5, so adjacency is irrelevant) and <=16 distinct (Chwat,
  Para_Lander). Per-subtune master_vol rides `DmcSong.master_vol` already;
  per-player idle priming is global-only but verified UNREAD for the cluster
  (build B with A's priming still FULL) — a per-subtune-priming member would
  show as a partial, not a wrong build.
- **Regression safety (proven):** the >=2-DISTINCT-player-dispatch signature
  never coincides with a FULL single-player member — census of all 5401
  family-1 members found 17 compilations, ALL previously partial/error/
  unsupported, NONE full. Both `dmc_build_one` and the family batch fall back to
  the single-player path on any merge/compose failure, so an unmergeable
  compilation keeps its prior status.
- **Landed (verified FULL):** Abyssal_Karma (2p, 5 subtunes), Sharkz (2p, 6),
  Para_Lander/Race_n_Smash/Chwat/Poing_Ultra (compact-remap), **Balloonacy
  (4p, 7 subtunes — 2026-07-10)**. RESIDUE (fall back, 0 regr): 3 filter
  OVERRUN (repeat>5 — Zap_Zone/Protox-1/Mission_Moon, need an overrun-adjacency-
  preserving window); 1 instrument overflow (Heavy_Metal, 30 > 28); the
  remaining per-player `locate` residue (Lane_Crazy/Wiz_Max/Goldrake_plus_2/
  Mystery/Rogue_Ninja) is now unblocked by the region-bounded locate below but
  unverified this round (deferred to the next batch). DUAL-PLAYER emit (composer
  multi-player) is the alternative for the unmergeable tail.
- **PER-PLAYER `locate` — REGION-BOUNDED (2026-07-10, Balloonacy, +1 FULL):** a
  co-packed player can be uniformly relocated for CODE + DATA TABLES yet carry
  DEAD-CODE JMPs into a SIBLING player's canonical code (an un-relocated
  `JMP $1591` when the live path uses its own `$3591`; ground truth `--pc-trace`
  = the player runs entirely in its own `$Xxxx` page, the `$1xxx` jumps never
  execute). The static `_instrs` trace follows them, so every opcode-window
  signature matches TWICE (once per player) → every site ambiguous → `locate`
  returns None → whole compilation falls to single-player. FIX:
  `dataflow.locate(region=(base, base+0x900))` bounds the located instructions
  to the forced player's own code window; the sibling's block sorts outside the
  range (the player's own block stays contiguous, signature windows intact) so
  sites are unique again. `base_override`-only — the general single-player path
  passes `region=None` (a re-assembled player may spread code past a fixed
  window). Regression-safe: can only turn ambiguous-None into a unique match.
- **INSTRUMENT-POOL fit via OFFTABLE-UNION dedup (2026-07-10, Balloonacy; C8
  sibling):** after the locate fix the 4-player merge overflowed the 28-inst
  5-bit id cap (29 > 28). The tightest pair differed ONLY in `offtable_freq` —
  a C6 reachability artifact (which wave-offset/note the instrument was played
  at), NOT intrinsic content. `merge_models` now keys the dedup on everything
  EXCEPT `offtable_freq` and carries the UNION of records per merged id
  (Principle Rule 1 — cluster by behavior; each record fires only for its own
  (off,note), inert for a song that never plays it). A record COLLISION (same
  (off,note) → different (lo,hi) across the two players' freq tables) refuses
  the union → distinct ids. 29 → 28. Regression-safe: only `merge_models`;
  every currently-FULL compilation keeps its identical instrument count
  (offtable-union changes nothing when no two insts share a base key).
- **HETEROGENEOUS compilation — DMC players + a distinct dmc_sfx sub-player
  (2026-07-10, Canyon_Tank_Duel, Bayliss; +1 FULL, 13/13 subtunes):** the packed
  players need NOT all be the same engine. Canyon packs 2 canonical DMC music
  players ($1000/$2000) + a tiny (~257 B) CUSTOM SFX sequencer at $3000 — its
  own note/instrument/waveform format, NOT DMC (also in Widding's
  Empire_Strikes_Back @ $3D00; two authors → a shared DMC-editor SFX sub-player,
  named `dmc_sfx`). Three pieces, all landed:
  1. **Detection from the WRAPPER TABLE, not a JT scan.** `_canon_jt_bases`
     required the canonical `4C b+1D 4C b+85` head and MISSED the re-assembled
     dmc_sfx player (jump table at +$1B2/+$F0). FIX: `detect_compilation` now
     derives the player bases from the dispatch wrapper's own base-hi `LDA
     abs,X` table (the authoritative list of what it selects), each validated by
     the RELOCATION-invariant three-JMP head (`_is_player_base`: JMP at
     +0/+3/+6). Regression-safe: keeps the >=2-DISTINCT-player gate + the
     merge-fallback; only WIDENS which bases are recognized. (Also newly detects
     Empire as a 4-player heterogeneous compilation.)
  2. **dmc_sfx migrated as a typed USF engine** (NOT opaque bytes / a §8 engine
     library). New `dmc_sfx {}` block + `dmcsfx`-kind subtunes carry the shared
     musical content: a rotating filter-cutoff LFO, an arp pitch-program table,
     tuning tables (extended over the off-table reads), 8 instruments (each a
     4-phase ctrl/freqbase timbre+pitch modulation + envelope/PW), 8 song
     records, and the shared initial voice state (a song sets up only ITS voice;
     the others play from file-image leftover = a typed `voice_init`). One quirk:
     a glide can push the freq index past the 96-entry table → an off-table read;
     mostly static code bytes captured as extended tuning (C6), the ONE live one
     ($30F1 = the play counter) reproduced by a composer redirect at
     `live_counter_fidx` (C11 state-as-data). Extract `sfx_engine.py`
     (+ a pure-Python reference interpreter reading ONLY the typed model — proves
     completeness); composer `sfx_composer.py` (a clean 6502 re-implementation).
  3. **Heterogeneous composer dispatch** (`build_dmc_compilation_sid`): emit BOTH
     the DMC engine and the dmc_sfx interpreter into one image behind a
     per-subtune stub at $1000 — init(A=subtune) latches the owning engine +
     routes with the engine-local index, play jumps to the latched engine. Same
     "one engine per subtune, sequential" shape as the 2SID dispatcher, but
     per-subtune-selected (only one runs) rather than parallel.
  Regression-safe by construction: the whole path is gated on `usf.dmc_sfx`
  presence (single-player + homogeneous-compilation members never touch it) and
  on the SFX-player detection (an existing wide-family invariant: the
  >=2-distinct-player-dispatch signature never coincides with a FULL single
  player); write_dmc_compilation_usf falls back to single-player on any failure.
- **OBSERVE the dispatch, don't parse it (2026-07-22, Defuzion_3, +1 FULL;
  C18/C27 method applied to C31).** The static wrapper decode assumes the
  index register IS the subtune and that the base table holds page HI-bytes
  only (JMP lo-bytes fixed at $00, players being page-aligned). That is one
  wrapper shape among several: Defuzion_3 SCALES the index (`ASL A; TAX` ->
  X = subtune*2) and patches full lo/hi VECTOR PAIRS, so every candidate
  table decodes to interleaved garbage ($5000, $0000, $6000, ...) and
  detection gives up — the member falls to the single-player path and decodes
  EVERY subtune from the start player (sub 0 FULL, the rest diverging at
  write ~1). This is the second widening the static parser has needed (the
  first was Canyon's re-assembled base); stop teaching it shapes. FIX:
  `_observe_dispatch` runs the member's own init with A = subtune under py65
  and records where it LANDS and what A it carries there — the landing is the
  selected player base, A is that player's song number, whatever arithmetic
  the wrapper used. Reload the image per subtune (the dispatch is SMC).
  Two disciplines make it zero-regression: it runs only as a LATER pass (the
  static decode wins whenever it resolves) and is pre-gated on the image
  carrying >=2 page-aligned player bases, so single-player members never pay
  for the emulation. **TRAP — it cannot tell a compilation from a MULTI-SID
  member by itself:** a 2SID wrapper that gates its per-chip calls on the
  subtune (Rayden: sub 0 = both chips, 1 = chip 1, 2 = chip 2) makes different
  subtunes LAND on different players, which is exactly a compilation's
  signature. All 14 Rayden 2SID members false-positived until the PSID header
  chip count was added as the discriminator (harmless in the build path, which
  checks 2SID first — but a latent trap the moment 2SID detection slips).
- **RECORD 0 must keep merged SLOT 0 (2026-07-22, Defuzion_3).** The engine's
  note-init cache is init-cleared to 0, so a voice idling before its first
  note runs instrument RECORD 0's pulse/wave mechanism — which is exactly why
  the single-player extract force-includes record 0 as USF slot 0 (RE_NOTES
  "idle-note voice_state priming"). `merge_models` rebuilt the pool from
  ROW-REFERENCED instruments only, so record 0 lost that slot and every idling
  voice in every compilation ran whichever instrument happened to sort first.
  Invisible until a voice idles for a whole song: Defuzion_3 sub 3's V3 track
  is a bare `$FE` stop, and the rebuild wrote PW lo $00 where the orig writes
  $40. FIX: seed the pool with the start player's record 0 before the
  row-referenced pass; the dedup collapses it into an identical played
  instrument, so a member whose record 0 is already played keeps its exact
  pool size. NB most compilations' players DISAGREE on record 0 (13 of 18
  measured, including 6 currently-FULL) — so raising on disagreement is NOT
  available; slot 0 carries the START player's record and a member whose
  idling voice belongs to another player stays partial (honest residue, not a
  wrong build).
- **IDLE PRIMING IS PER-SUBTUNE (2026-07-22, Defuzion_3) — this CLOSES the
  "per-player idle priming is global-only" residue noted above.** Each packed
  player has its OWN uncleared work-file leftovers (Defuzion_3's three players
  prime curnote 0/0/48) and each subtune runs exactly one player, so the
  priming is a per-subtune fact. It rides `subtune { init { voice N {
  note / gate_mask / dur_reload } } }` instead of the file-level `init` block.
  NO SCHEMA ADDITION — `InitVoice` already carries these fields at both
  levels, which is the same split the schema documents for `speed_ctr_init`
  ("file-level init for single engines; per-subtune init for compound ones").
  Composer side: the priming tables widen to `n_subtunes*3` and the init
  indexes them by `subtune*3 + voice`, GATED on some subtune actually stating
  a value that differs from the file-level block — so every existing member
  keeps its `lda inote,x` form and a byte-identical image (proven: 600/600
  stored non-compilation FULL members rebuilt byte-identical from their stored
  `.usf`).
- **IDLE WAVE IS PER-SUBTUNE TOO (2026-07-30, Pievspie/Mission_Moon) — the same
  per-player fact as the priming above, one level up.** The idle wave is the
  cleared-cache wave PROGRAM a voice's effects walk before its first note (the
  wave-table walk from position 0 = `wave_programs[0]`); the merge collapsed it
  to the START player's, so a subtune whose player's wave table DIFFERS at pos 0
  ran the wrong lead-in wave. Mission_Moon: player 1's V2 idles, and on player
  0's idle wave its freq-base cache diverges — its off-table freq read (idx 233
  = fbl+1, C11 live-served) reads $8F vs orig $F7 → sub 1 partial (sub 0 has no
  divergently-idling voice, so it was already FULL). PROOF: forcing merged
  `idle_wave = player1's` → BOTH subtunes FULL. FIX (all three layers):
  - **Merge** sets per-song `DmcSong.idle_wave = models[pidx].idle_wave`
    (compilation.py, mirroring `idle_notes`).
  - **to_usf** emits it as the PRE-EXISTING `MusicSubtune.wave_programs[0]`
    override (added for Super_Tau-Zeta's V5 idle program but never consumed by
    the V4 composer) — ONLY where `song.idle_wave != m.idle_wave`, so a subtune
    inheriting the file-level idle emits nothing.
  - **Composer** appends each distinct override to the wave pool (`add_prog`),
    records `sub_iwpos[s]` = its pool position (0 = inherit the file-level idle
    at pool pos 0), and primes each subtune's voices' `wavepos` from an `iwpos`
    table in the `ini_v` loop — reusing `per_sub_prime`'s `subtune*3+voice`
    addressing (per_sub_iwave forces it on). The idle wave is per-SUBTUNE, so
    all 3 voices of a subtune share its position.
  GATED throughout: absent unless a compilation's packed players actually
  disagree on the idle wave, so single-player + same-idle-wave members are
  byte-identical (golden gate: only Mission_Moon partial->FULL and Balloonacy
  FULL->FULL changed across the sample). INCOMPATIBLE with the layout-preserving
  / positional wave pools (`wavepos_layout` / `wavepos_positional`) which pin
  `wavepos` to the orig's live $177A — there the override is IGNORED (keeps the
  collapsed file-level idle, byte-identical to the pre-fix build, so a
  layout-pool compilation can never regress; a member that genuinely needs it
  stays honest residue, never a build failure).
- **INSTRUMENT NUMBER IS SONIFIED via the off-table `ioff` read (2026-07-30,
  Pinov_Vox/Goldrake) — the merge RENUMBERS instruments, but the sonified value
  is the ORIG per-player number.** `ioff` ($174D,x) = the current instrument's
  record byte-offset = orig inst# * 11 (exact 6502 carry chain); it is read
  off-table and PLAYED when a note index wraps to idx 166-168 (C11 live-served
  via `DMC_OFFTABLE_STATE`). The merge packs each player's instruments into one
  renumbered pool, so the composer's `ioffval = _inst_offset(slot)` sonifies the
  MERGED slot's number, not the orig. Goldrake: player 1's local inst #0 (ioff
  $00) became merged id 5, so V3's off-table read played $2C (=4*11) vs orig $00
  — a deep mid-song value divergence (frame ~1630), player 1 STANDALONE FULL.
  Signature: the diverging freq value is an exact multiple of 11. PROOF: forcing
  the correct orig `ioffval` per merged instrument → sub 1 FULL. FIX:
  - `DmcInstrument.record_offset` + USF `Instrument.record_offset` (a per-
    instrument value, precedent `wave_table_pos`): the ORIG offset. The composer
    emits `ioffval[k] = i.record_offset or _inst_offset(slot)`.
  - `merge_models` stamps `ni.record_offset = _inst_offset(old_orig_local#)`
    BEFORE the dedup key (so it RIDES the key — two players' identical-content
    instruments at DIFFERENT table positions sonify different ioff and must NOT
    share a slot) and nulls it again when it equals the slot default (so a
    non-renumbered instrument stays byte-identical).
  - to_usf emits it only when set. GATED: single-player members never set it
    (byte-identical); a compilation emits it only for renumbered instruments.
    Golden gate: 29 identical + 0 single-player changed; the 8 changed
    compilations = Goldrake partial->FULL + 7 FULL->FULL (verdict-preserved).
- **THE RELOCATING WRAPPER (2026-07-22, Pour_le_merite) — the packed player
  need not be IN THE FILE IMAGE AT ALL.** The wrapper COPIES a player into RAM
  per subtune (`$2000->$4700`, `$9409->$1000`, page loop + byte tail) and only
  then dispatches, so a detector that scans the image can never see the second
  player. This is C26 ("read what the ENGINE reads") applied to C31 DETECTION
  rather than to song data. Four parts, each of which bit separately:
  - **Pre-gate.** The ">=2 in-image player bases" gate structurally cannot
    admit these. Second gate: **>=1 in-image base AND a PSID init vector that
    does not lead into any of them** — i.e. a wrapper runs before any player.
    An ordinary member's init vector IS its player's jump table, so it fails
    instantly: measured over all 5401 DMC f1 members the whole detection sweep
    costs **2.7 s**, detects 21 (was 14), loses NONE, and every newly detected
    member was already partial (no FULL changes build path). Cheap + zero
    regression risk — the gate to reach for when a detector must widen.
  - **Drop the load-address FLOOR on anything read from RAM.** A wrapper can
    copy a player BELOW the load address (Pour_le_merite loads at $8000 and
    relocates down to $1000), so `load <= addr` — a sound guard for image
    reads — is exactly WRONG here. It bit in three places: the landing test,
    the jump-table layout check, and the instrument-base assert.
  - **Snapshot AT THE LANDING, not post-init.** Run init(A=sub) and stop the
    moment control reaches the player base. Running init to completion looks
    equivalent and is not: the leftover state the extract reads as PRIMING
    (the $D417 routing shadow, idle notes/masks) is PRECISELY what a player's
    own init overwrites. The landing snapshot is the exact analogue of the
    file image an in-image member is extracted from.
  - **Every layer must share that memory view — including the PROBE TABLE.**
    This is C9's 5th occurrence recurring one layer further out than r83b
    closed it: reading a probe at a base the image doesn't carry returns
    zeros, so every wedge comes back DEFAULTED (silently wrong music, not a
    refusal). All 14 `_load(path)` probes take the subtune.
- **TWO MORE per-player facts the merge collapsed to the START player** (same
  class as the per-subtune idle priming above — the merge keeps `b.<field>`
  for every subtune, so a subtune silently gets ANOTHER player's value):
  - `d417_shadow` -> `DmcSong.d417_shadow`, emitted into the per-subtune
    `init.sid.filter.res_routing` the schema ALREADY carries (NO schema
    addition — trichotomy §4.2 priming, same file-level-vs-per-subtune split).
    Pour_le_merite sub 0 was primed $01 where its own player primes $02.
  - the filter-def POST-INIT re-read (the 'Ed' members' 272-byte window) ran
    with the DEFAULT subtune — one whose wrapper never copies this player into
    place — so the window came back all zeros and every filter def decoded
    EMPTY. TELL: a relocated player whose filter defs are uniformly zero while
    the bytes at the located table address are plainly non-zero. Any
    memory re-read inside an extract must inherit the extract's memory view.
- **A THIRD per-player fact — and this one splits in TWO places** (the
  OFF-TABLE window, Para_Lander_DX 3/3, 2026-07-23). Each packed player's freq
  table overruns into ITS OWN state block, so the same window index names a
  DIFFERENT byte per player. Both halves must be fixed or the member stays
  partial:
  - **EXTRACT — a per-player runtime measurement must run the FILE subtune
    that selects that player.** The per-player extract numbers songs LOCALLY
    (0, 1, ...) and `_correct_offtable_postinit` fed those straight to
    `siddump --subtune`, so player 1's song 0 was sampled in file subtune 0 —
    which runs a DIFFERENT player and therefore leaves this player's work RAM
    at the never-inited FILE-IMAGE LEFTOVER. The captured byte is then
    well-formed, stable, and wrong. Cure: `DMCV4Config.song_subtunes`
    (player song -> PSID subtune), built in `_player_cfg` from `spec['map']`,
    consumed by every runtime sample. **This is the same defect shape as the
    filter-def post-init re-read above** — read that one as the general rule:
    *any* measurement inside a per-player extract inherits the player's
    subtune, not the file's. **The rule has TWO axes — the SUBTUNE and the
    ADDRESSES.** Round 89 fixed `_correct_offtable_postinit` (subtune only, via
    `song_subtunes`) but its SIBLING `_correct_offtable_eventdriven` was missed
    (Rogue_Ninja, 2/2, 2026-07-23): it ran siddump with NO `--subtune` (start
    song = the START player) AND watched HARDCODED canon state addresses
    (`$1783/$1012/$172F/$1732` = player 0's), so for a non-start packed player
    it captured the WRONG player's off-table reads and OVERWROTE a record the
    post-init pass had already resolved correctly (player-1 idx 97 = $B7,
    clobbered by player-0's $1708 = $D6 — both a per-player static byte). Cure:
    `_eventdriven_addrs` derives the watched tuples from cfg (CN/INS
    base-relative; Y/BLO/BHI freq-table-relative) so a RELOCATED player's state
    is watched, and the capture runs `song_subtunes.values()`. A canon
    single-player computes the exact canon addresses + start song -> byte-
    identical. LESSON: when you make ONE runtime measurement per-player-aware,
    grep for its siblings — a second constant-looking, well-formed, WRONG byte
    hides in each one you skip.
  - **COMPOSER — an idx-keyed FILE-LEVEL table cannot hold a per-player
    fact.** The off-table window is one 160-byte array; two players' records
    at the same position silently resolved last-wins. Cure: attribute each
    record to the subtunes whose ROWS play its instrument (derivable from USF
    content — no schema addition), and where subtunes disagree, have init
    write those positions for the subtune it was called with. Write EVERY
    conflicting position on EVERY init, not just the differing ones, or a
    subtune inherits its predecessor's patch. GATE on an actual disagreement
    so conflict-free members stay byte-identical.
  - TELL for the pair: an off-table read whose orig value is neither the file
    image NOR any post-init sample of the start subtune, on a member with >=2
    player bases. Exposure census is cheap and complete for the FULL side —
    scan the STORED `.usf` for two instruments naming one window position with
    different bytes (16 of 5401 f1 members; all held, 0 regressed).
  - **SINGLE-PLAYER FORM — the same window fact can be per-SUBTUNE with ONE
    player and a SHARED instrument (Assassins 2/2 + Useless_1994 2/2,
    2026-07-23, round 99).** The track-ptr slots ($1707-$170C) are
    per-subtune init state; a record reached by 2+ subtunes reads a
    DIFFERENT constant in each (Assassins inst 21 idx 98 = $1709: sub 0
    $80, sub 1 $CE). Instrument-usage attribution can't disagree (both
    subtunes play the SAME instrument), so `_correct_offtable_postinit`'s
    all-agree check fell back to the start-song sample — every non-start
    subtune read the wrong pitch, a documented-but-unserved limitation.
    Cure with ZERO composer/schema change
    (`engine_model._split_offtable_by_subtune`): the extract records
    per-subtune sampled values on disagreement (`m.offtable_song_values`,
    collected in `pick`'s loop) and SPLITS the instrument per VALUE-CLASS —
    clone + remap the non-start classes' rows — so each subtune USES an
    instrument carrying its own values, which is exactly the disagreement
    `ovr_sub` already detects and patches at init. Honest representation:
    the subtunes genuinely hear different pitches at that read (Rule 1
