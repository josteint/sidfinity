### C36 — a PC-triggered bus tap false-fires on DATA reads of the trigger address

**Status:** logged (1×, DMC For_Party / `--reinit-snapshot`, 2026-07-25)

## Problem class

Any observation hook that watches the emulated **bus** for "the CPU reached
PC X" — a capture trigger, a landing detector, a coverage probe — sees only
`cpuRead(addr)` events, and the bus cannot tell an **opcode fetch** from a
**data read**. Player code and player data share the address space, so the
trigger address itself can be read as *data* during normal play (a table walk,
an off-table read, a pointer landing on it). A bare `addr == trigPC` check then
fires long before (or without) the code ever executing there, and the capture
silently reports a coherent-looking WRONG snapshot.

The existing play-vector counter (`setPlayAddr`) gets away with the bare check
only because a PSID play vector is never read as data in practice — that
guarantee does NOT transfer to an arbitrary watched PC.

## How it presented

`siddump --reinit-snapshot` (Phase 1 of `docs/siddump_native_capture_plan.md`)
was to capture the C19 shape-B reinit COLD/WARM RAM windows from libsidplayfp,
replacing py65. COLD matched py65 byte-identically; WARM differed 79/2048
bytes with plausible-looking values (a real mid-song state, just the wrong
moment). The tell that unmasked it: the **C20-style control** — re-verifying
the py65 baseline FRESH under current code — showed py65's answer was genuinely
FULL, so the divergence had to be the new tap, not py65 drift. A memtrace then
showed the wedge address `$10DD` read as **data at frame 200**, ~9600 frames
before the reinit executes it.

(A second confusion stacked on top: `writelog_capture` returns only frames
that HAVE writes, so its frame indices are compacted vs raw siddump frames —
9538 compacted = 9845 raw. Localize with same-process captures before
comparing frame numbers across tools.)

## Canonical solution

Discriminate **execution** from data reads by the 6502's bus signature:
executing code at `trigPC` produces **≥3 consecutive ascending reads**
(`opcode @PC`, `operand @PC+1`, `next fetch @PC+2`) with no intervening read.
No data access pattern can produce that run: every instruction interleaves its
own opcode fetch between data reads; an indirect-pointer read yields only a
2-run; an RMW dummy re-read repeats the same address (run resets). Implement
as a tiny run tracker in the bus hook: `run = (addr == last+1) ? run+1 : 1`,
fire when `run >= 3 && addr == trigPC+2`. Lives in
`tools/libsidplayfp-overlay/src/c64/c64cpu.h` (`m_reinitRun`).

Boundary: an IRQ landing between the two instructions would break the run —
but a trigger inside a play() IRQ handler runs with the I flag set, so for
in-play wedges the miss window is nonexistent. For a trigger in non-IRQ code,
consider the miss window before relying on a single-shot capture.

6510-vs-6502 audit (2026-07-25, from the MOS6510 implementation, not the
datasheet): VIC BA/RDY cycle stealing is stall-immune for the run tracker —
`MOS6510::eventWithSteals` WAITS a stalled read cycle and executes it once
when RDY returns (only `nosteal` write cycles proceed during a stall), so a
badline never repeats or interleaves reads. The 6510's I/O port at
`$0000/$0001` is a SNAPSHOT boundary, not a trigger one: the window is read
via `mmu.readMemByte` (the RAM view), so a window covering $0000/$0001 would
return the RAM under the port, not the port registers (the same RAM-vs-CPU-eye
split as `--memwatch` vs `--peek-post-init`) — relevant if a C29-class
zp-sonifying member is ever captured with a zp window.

Validation pattern for any such tap: **cross-emulator byte-identity** — the
captured windows must match an independent emulator's capture byte-for-byte
(For_Party: 2×2048 bytes vs py65, after which the py65 path was deleted).
That check also subsumes the non-perturbation gate: a tap that perturbed
emulation could not reproduce an independent engine's deep-playback state.

## Failed alternative (why the obvious form is wrong)

The bare `addr == trigPC` check, generalized from the play-vector counter.
It produced a well-formed, plausible, WRONG capture — the standard
"measurement tool answering confidently instead of refusing" failure
(cf. `pipelines/dmc/state_addr.py`'s refusal rule).

## Consumers (seen)

- `siddump --reinit-snapshot` / `c64cpubus::setReinitSnapshot` (DMC shape-B
  ghost capture; occurrence status in [[project_dmc]]).
- `siddump --pc-watch` / `c64cpubus::setPcWatch` (executed-PC event stream —
  the generalized form: exact PCs + low-byte patterns, A/X/Y + play-index +
  RAM windows per event; DMC `_observe_dispatch` landing observation).

- **KNOWN GAP (2026-07-29, r137 — recorded on first sight, build the general
  tap on recurrence):** the ≥3-consecutive-ascending discriminator is
  STRUCTURALLY BLIND to 2-byte indirect-indexed sites — `LDA ($f8),y`'s bus
  runs opcode@PC, operand@PC+1, then the POINTER PAIR at zp and the data
  read, so PC+2 never follows consecutively and the tap never fires
  (verified: canon DMC $110F yields zero events while the 3-byte sites $10D2
  and $1119 fire normally). Workaround that served r137: watch a 3-byte
  instruction AT THE SAME CALL DEPTH (the track-fetch entry base+$D2) with
  `--pc-watch-abs` — the captured window is what the subsequent indirect
  reads see. A future 2-byte-site discriminator would key on the constant-zp
  pointer-pair read signature; per this entry's own rule it needs the
  cross-emulator byte-identity validation gate before trusting a single
  capture.

- **SECOND GAP — INTERRUPT-PACED MEMBERS UNDER-COUNT (2026-08-31,
  Rayden_Digi).** The discriminator needs three consecutive ascending reads,
  and an interrupt that fires often enough will land BETWEEN a watched
  instruction's opcode and operand fetches, breaking the run. So on a member
  whose NMI fires every ~105-210 cycles, `--pc-watch` reports ~90% of the
  executions: counting the digi sequencer's per-frame calls gave 1.79
  calls/frame where the write stream proves exactly 2.0025. The loss is
  SILENT and looks like a real rate — it does not read as a truncated or
  malformed capture.

  TELL: a pc-watch count that lands a few percent under a clean integer or
  a clean multiple of the frame rate, on a member with a fast periodic
  interrupt. RULE: do not use `--pc-watch` as a RATE meter on an
  interrupt-paced member. Prefer a measurement that counts the WORK rather
  than the executions — the write stream itself, fitted (Rayden's score
  model gives cycles-per-tick to ~0.1%), or `--memwatch-on-write` on a
  register the routine always touches. `--pc-watch` remains sound for
  "where did it land" and "what were A/X/Y" — a MISSED event does not make
  a REPORTED event wrong; only the count is unreliable.

  Note this compounds the first gap: the Rayden tick's own entry is a
  2-byte `dec zp`, whose third bus read is the zero-page operand rather
  than PC+2, so it never fires at all. Watching the module head's 3-byte
  `jmp` fires, but under-counts as above.
