### C36 — a PC-triggered bus tap false-fires on DATA reads of the trigger address

**Status:** logged (1×, DMC For_Party / `--reinit-snapshot`, 2026-07-25)

## Problem class

Any observation hook that watches the emulated **bus** for "the CPU reached
PC X" — a capture trigger, a landing detector, a coverage probe — sees only
`cpuRead(addr)` events, and the bus cannot tell an **opcode fetch** from a
**data read**. Player code and player data share the address space, so the
trigger address itself can be read as *data* during normal play (a table walk,
an off-table read, a pointer landing on it). A bare `addr == trigPC` check then
fires long before (or without) the code ever executing there, and the capture
silently reports a coherent-looking WRONG snapshot.

The existing play-vector counter (`setPlayAddr`) gets away with the bare check
only because a PSID play vector is never read as data in practice — that
guarantee does NOT transfer to an arbitrary watched PC.

## How it presented

`siddump --reinit-snapshot` (Phase 1 of `docs/siddump_native_capture_plan.md`)
was to capture the C19 shape-B reinit COLD/WARM RAM windows from libsidplayfp,
replacing py65. COLD matched py65 byte-identically; WARM differed 79/2048
bytes with plausible-looking values (a real mid-song state, just the wrong
moment). The tell that unmasked it: the **C20-style control** — re-verifying
the py65 baseline FRESH under current code — showed py65's answer was genuinely
FULL, so the divergence had to be the new tap, not py65 drift. A memtrace then
showed the wedge address `$10DD` read as **data at frame 200**, ~9600 frames
before the reinit executes it.

(A second confusion stacked on top: `writelog_capture` returns only frames
that HAVE writes, so its frame indices are compacted vs raw siddump frames —
9538 compacted = 9845 raw. Localize with same-process captures before
comparing frame numbers across tools.)

## Canonical solution

Discriminate **execution** from data reads by the 6502's bus signature:
executing code at `trigPC` produces **≥3 consecutive ascending reads**
(`opcode @PC`, `operand @PC+1`, `next fetch @PC+2`) with no intervening read.
No data access pattern can produce that run: every instruction interleaves its
own opcode fetch between data reads; an indirect-pointer read yields only a
2-run; an RMW dummy re-read repeats the same address (run resets). Implement
as a tiny run tracker in the bus hook: `run = (addr == last+1) ? run+1 : 1`,
fire when `run >= 3 && addr == trigPC+2`. Lives in
`tools/libsidplayfp-overlay/src/c64/c64cpu.h` (`m_reinitRun`).

Boundary: an IRQ landing between the two instructions would break the run —
but a trigger inside a play() IRQ handler runs with the I flag set, so for
in-play wedges the miss window is nonexistent. For a trigger in non-IRQ code,
consider the miss window before relying on a single-shot capture.

Validation pattern for any such tap: **cross-emulator byte-identity** — the
captured windows must match an independent emulator's capture byte-for-byte
(For_Party: 2×2048 bytes vs py65, after which the py65 path was deleted).
That check also subsumes the non-perturbation gate: a tap that perturbed
emulation could not reproduce an independent engine's deep-playback state.

## Failed alternative (why the obvious form is wrong)

The bare `addr == trigPC` check, generalized from the play-vector counter.
It produced a well-formed, plausible, WRONG capture — the standard
"measurement tool answering confidently instead of refusing" failure
(cf. `dmc_state_addr.py`'s refusal rule).
