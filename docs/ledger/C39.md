### C39 — a data table the extraction reads at a FIXED OFFSET from another table is a packer-patched OPERAND that can relocate INDEPENDENTLY

- **Problem class:** the extraction reads table B at a hard-coded relative
  offset from table A (e.g. DMC filter step DURATIONS at `op_filtdef + 10`,
  interleaved inside a 16-byte filter-def record). But the player reads B via
  its OWN `LDA base,Y` operand, and the packer relocates each operand
  independently — so on some members B is NOT at A + the assumed offset. The
  extraction then reads the wrong bytes and decodes wrong musical content, while
  the file "looks" internally consistent (A is where the extraction expects; only
  B moved). This is the project's KEY dataflow lesson (packer-patched operands →
  extract by dataflow, never a fixed offset) hitting a table the extraction had
  hardcoded instead of resolving from code.
- **TELL:** a table-driven value follows the RIGHT initial values, then diverges
  into a DIFFERENT CONTOUR (Vai/Hardtechno: filter cutoff matches 3 frames then
  the orig walks a +$60/frame wrap while the rebuild does a −1 ramp — the rebuild
  advanced to the next program step because it read a non-zero duration; the orig
  read duration 0 and never advanced). Ground-truth `siddump --memwatch-on-write
  <reg> <step-caches>` shows a size/duration cache that does NOT match the decoded
  record byte (Hardtechno: `fdu` $1722 = $00, not the record+10 byte $02).
- **Canonical solution:** resolve B's table address from the PLAY body's operand
  (`_rd16(mem, base + <routine offset> + <operand offset>)`), gated on the canon
  opcode so a re-assembled/relocated routine falls back to the assumed offset
  (`None` → byte-identical). DMC filter defs: the routine is canon `$13E6`
  (`LDA fsz,Y / STA $1721 / LDA fdu,Y / STA $1722`, fbase = filter_def*16), the
  two `LDA abs,Y` operands at base+$3E7 (sizes) / base+$3ED (durations);
  `_decode_filter_def(…, fsz_tab, fdu_tab)` then reads
  `(signed8(mem[fsz_tab + def*16 + k]), mem[fdu_tab + def*16 + k])`.
- **Regression-safety:** for the common member the operand IS at the assumed
  offset (sizes op_filtdef+4, durs op_filtdef+10) → identical read → byte-
  identical. No FULL member regresses: a filter-using FULL member already had the
  duration at +10 (else it would have been partial), and the operand-resolved read
  is GROUND TRUTH — it can only make the write stream more correct. Verify by a
  census over the corpus (how many members have B not at A+offset) — the set is
  the fix's entire exposure.
- **Boundary / generalization:** applies to ANY table the extraction addresses as
  `<other table> + fixed offset` rather than resolving the operand — audit the
  DMC extract's remaining fixed-offset assumptions (wave sub-tables, instrument
  sub-fields) if a similar "right start, wrong contour" divergence appears in
  those. Distinct from C2 (byte-INDEX runs off the END of a table) — here the
  index is fine, the table BASE is wrong.
- **Consumers (seen):** DMC filter step-duration table — Vai/Hardtechno
  (fdu at op_filtdef+165) + Vai/Sad_End (op_filtdef−145). See
  [[project_dmc]] round 160.
- **Status:** logged (2×, both Vai; the census found no other carrier in 7457
  canon-head filter members).
