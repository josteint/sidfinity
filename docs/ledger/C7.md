### C7 — ANTI-PATTERN: original bytes carrying musical intent that bypass / opaquely sit in the USF
- **The smell (user's, since project inception):** bytes from the original SID
  that encode MUSICAL information end up in the output SID without being produced
  from first principles by musical content in the USF. Three severities — keep
  them distinct:
  - **Class A — leapfrog:** orig bytes → output, BYPASSING the USF entirely. The
    ML never sees them. Worst when the bytes are musical (A2). FC's
    `compose_fc_asm`/`build_via_asm`/`_emit_verbatim_region` were the original
    byte-copy leapfrog and are session-1 scaffold — gated off live (every config
    sets `emit_data_from_usf=True`); the dead functions were removed 2026-06-18.
    **A3 — the PARAM-SHAPED leapfrog (found 2026-07-22, fc_standard).** The
    status line here used to read "NONE across the live verdict pipelines"; that
    was true only of BYTE copies. A probe can lift an orig byte into a *config
    field*, and the composer then emits from the field — orig → output, never
    through the USF, just not shaped like a blob. `fc_standard` carries three:
    `std_vibrato_stale_tail` ($2046 build variant, 32 carriers, load-bearing on
    all 22 tested), `std_glide_hi_reg` ($1B3F operand, 20 carriers, load-bearing
    on 6) and `std_arp3_init` ($1E86-8 seed, load-bearing on exactly 1 —
    Intro_Music_I's slot 0 = $E0). FC's `params {}` block was EMPTY, so the USF
    was not the complete build spec for ~39 of the 2530 FULL members.
    CLOSED 2026-07-22: all three now ride in `params`. TELL: a per-member value
    that varies WITHIN one engine family and reaches the composer as a
    constructor argument. (Contrast the 31 fc_standard fields that are family
    CONSTANTS — those are mechanism and correctly live in the engine, per §7's
    "the engine may hold mechanism".) Distinguishing test is C7's usual one, but
    it must be run on the WRITE STREAM, not on emitted bytes — see the
    byte-identity warning below. Open; see [[project_fc_principled_composer]].
  - **Class B — opaque blob IN the USF:** bytes round-trip through the USF (§9-clean)
    but as a raw content-by-reference list with no musical structure → the ML sees a
    black box. **`freq_overrun` is RESOLVED (2026-06-21):** both consumers (FC std +
    DMC v5) deconstructed to musical per-instrument `offtable_freq` frequencies via
    C7-option-(a) — see C6; the field itself is pending removal (plan Phase 7).
    Remaining B instances: `SfxSubtune.extended_freq` (Hubbard SFX off-table sweep),
    some Hubbard engines' 320-byte `freq_table` (192 musical + 128 state tail read by
    arp extension; the notenum-overlap engines — Commando itself is a clean 192).
  - **Class C — justified:** the bytes ARE the natural musical form (`freq_table`
    tuning, digi PCM). Not the anti-pattern.
- **Why B recurs (the mechanism):** an engine indexes PAST a freq table
  (`index = offset + note > table_size`) into its own state/scratch region, and
  those bytes get PLAYED as frequencies. The same bytes are BOTH engine state AND
  read-as-freq — content-by-reference captures them (write-stream correct) but
  presents them opaquely. Largely **B2** (state read as freq, incidental) not
  **B1** (deliberate extended tuning): the off-table bytes don't form a coherent
  monotonic tuning (Elysium window = state/scratch, not a tuning continuation).
- **Decision (per instance, the human's — surface, don't cargo-cult):**
  (a) **deconstruct to musical** — represent each off-table step's RESULTING freq
  as an absolute freq/note (hard: note-dependent → effectively an extended tuning
  table, and for B2 the extra entries are state-derived); (b) **document + minimize**
  — reachability-minimal capture, flagged "engine reads state-as-freq" (the ML sees
  a small, labeled blob; DMC's off-table capture IS minimized as of 2026-06-21 —
  per-instrument `offtable_freq` records, median 1/file, the old window gone);
  (c) **exclude** the tune as engine-quirk-dependent.
- **Status:** `methodology` (recurring). **Before adding any new content-by-reference
  / `bytes`-typed USF field, CONSULT this entry and pick (a)/(b)/(c) deliberately.**
  Audit hook: `/uready-review` should flag every content-by-reference/`bytes` USF
  field as a B-class candidate. (Distinct from C6, which is the off-table-freq
  TECHNIQUE; C7 is the anti-pattern lens over it + extended_freq + the freq_table tail.)
- **B-class audit RESOLVED (2026-07-06, user-ratified): `dual_freq_generator` +
  `dual_generator_steps`** (round 35, Taurus_02, sole corpus carrier; renamed from

## BYTE-IDENTITY IS A ONE-WAY GATE (2026-07-22)

Byte-identity of the rebuilt `.sid` is used across this repo as a cheap
equivalence gate (the carrier-refactor convention in CLAUDE.md, C33's gate,
C20's fifth layer). That inference runs in EXACTLY ONE direction:

    same bytes  =>  same write stream  =>  same verdict          (VALID)
    diff bytes  =>  different behaviour                          (INVALID)

The converse is false and it is easy to reach for when classifying a knob.
Worked example: asked whether three `fc_standard` config fields were audible,
the first pass flipped each and diffed the rebuilt `.sid`. All three changed
bytes, and the conclusion drawn was "all three are per-member musical content,
a §8 leak". Re-run on the WRITE STREAM (the Core Tenet's actual target), the
answer was completely different: `std_arp3_init` is an init SEED emitted as
`lda #$xx` — the immediate changes the image while the resulting stream is
identical (inert on 70/70 members, load-bearing on exactly 1). Two of the
three findings in the first pass were artifacts of the wrong oracle.

**Rule: to decide whether a parameter MATTERS, force a wrong value and verify
against the ORIGINAL.** "My two builds differ" is not evidence of audibility,
and "my two builds agree" is not evidence of inertness either — the code path
may simply not be reached by that member, so test real CARRIERS and report the
carrier count, not a single example (C19's "a default generalised from ONE
observed carrier is an un-probed hardcode in disguise").

**THE CONSTRUCTIVE FORM — the KNOCK-OUT SWEEP (2026-07-22, Music Assembler).**
The rule above says how to test ONE knob. When an engine hands you a whole
BLOCK of candidate state and the question is "which of these is content at
all?", run it as a sweep: for each key, zero it, rebuild, and diff the emitted
WRITE STREAM against the un-zeroed rebuild, over a SAMPLE of members (a short
12 s capture is enough — priming is a frame-1 phenomenon). Note this diffs two
of MY OWN builds, which the section above warns about — that is fine here
*because the oracle is the stream, not the bytes*: the question being asked is
"does this key reach emission at all", not "is my build right". Keys that never
move the stream on any member are not carried.

MA: 24 per-voice/scalar work-file leftovers → 10 never moved the stream. The
sweep is only half the method — **then explain the dead set from the engine, or
you have a coincidence, not a result.** Here the engine's init leaves `durctr`
at 0, so every voice FETCHES on frame 0, and that fetch overwrites
gmask/curnote/presetx/arppos before anything reads them; what survives is
exactly the state a fetch does NOT write, i.e. a voice idling mid-note. That
explanation is what makes the drop safe rather than sample-lucky, and it also
predicts WHICH members could still need a dead key (one whose first event is a
hold). Cheaper and far more honest than minting a typed field per leftover
"just in case" — 10 fields not added.

**COUNTING TRAP (same session).** The first carrier counts published for the
above were 4x too high (121 / 80 / "~146 members") because they were taken by
scanning a family batch's results jsonl WITHOUT deduplicating by path. A batch
that APPENDS on resume (FC's `fc_std_wide_results.jsonl`) accumulates one row
per member PER RUN, so `[r for r in rows if r['status']=='full']` counts
generations, not members: 10053 rows = 2530 members x ~4 runs. TELL: a member
printed more than once by a per-carrier listing. Always fold to
`{row['path']: row}` (last wins) before counting or sampling — and note this is
NOT the C20 stale-verdict layer (those rows are filtered by `code_hash`);
duplicates can all be current-code.
