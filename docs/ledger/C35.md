### C35 — one FILE, more than one COMPOSER (the `origin_engine` scaffold)

- **The problem class:** a single original packs players from DIFFERENT engine
  families behind a per-subtune dispatch wrapper — subtune 0 is played by one
  family's player, subtunes 1-2 by another's. Each subtune verifies fine on its
  own (they are independent write streams, C31), but the file cannot be STORED
  as one `.usf`, because nothing in the schema says which composer builds which
  subtune. Today that dispatch lives outside the USF entirely, in whichever
  caller happens to know the member's family.

- **Canonical solution:** `MusicSubtune.origin_engine` — each subtune names its
  engine family. Permitted EXACTLY when the file **demonstrably requires more
  than one COMPOSER**. Declared in `docs/the_principle.md` §8 as a Move-1
  scaffold; enforced by `src/usf/validate.py::_check_origin_engine`.

- **⚠ THE BOUNDARY IS "MORE THAN ONE COMPOSER", NOT "MORE THAN ONE ENGINE".**
  This is the whole entry. 5 Title Tunes packs FIVE fully independent Hubbard
  '85 sub-engines — each with its own init, play, freq table, instrument table
  and pattern data — and needs no tag at all: one composer serves all five via
  per-subtune `params` + globally renumbered instruments, and the unified build
  is **38% the size** of the earlier compound build (5/5 subtunes exact). A
  same-family plurality is a PARAMETERIZATION problem with a parametric answer.
  Reach for the tag only after that route has been tried and shown not to
  reach; "this file has several engines in it" is not the test.

- **Why it is allowed at all, when §8 forbids exactly this shape:** because
  the leak already exists and is currently INVISIBLE. There are ~6 composer
  entry points, the dispatch is caller-side, one stored `.usf` already carries
  `engine: goattracker_v1` in its params bag, and `UsfFile.dmc_sfx` +
  `DmcSfxSubtune` is already an engine-named block. Writing the dependency down
  does not create it; it makes it auditable and gives Move 1 a work list. The
  ML objection (§8's real harm — the audible-character knowledge living in
  Python instead of the training data) does not bite here, because no training
  happens before Move 1 and the field is gone by then.

- **Three constraints, all load-bearing:**
  1. **File/subtune level only, never inside an instrument or effect.** The
     asymmetry is structural, not stylistic: this field is deleted BY Move 1
     (with one engine-blind composer the permitting condition is false for
     every file, so it cannot outlive the unification even by neglect). A
     per-instrument engine `kind` is NOT deleted by Move 1 — which unifies
     composers, not representations — and would be permanent damage to the
     effect manifold (§7). One is self-cleaning; the other is forever.
  2. **Read by the DISPATCHER, never by an EMITTER.** It selects which
     composer runs; it must never shape that composer's output. A composer
     branching on it to decide what to emit is §8 in full.
  3. **Self-policing.** Validation refuses the field unless every music
     subtune names one AND >=2 distinct values appear. A file whose subtunes
     all agree needs one composer, so the tag states nothing — refusing that
     case is what stops the field becoming the cheap answer to any awkward
     migration, which is precisely how §8's leak kept re-emerging.

- **Status:** `logged` (2026-07-22). Carriers: the DMC + Music Assembler
  heterogeneous member (`Bayliss_Richard/Freespace_2075`, ledger C31), the
  DMC + `dmc_sfx` compilations, whose bespoke `UsfFile.dmc_sfx` block this
  generalises, and the DMC **V4 + V5** member
  (`Bayliss_Richard/Super_Tau-Zeta`, round 93 — V4 and V5 are different
  COMPOSERS, `compose_dmc_asm` vs `emit_v5_asm`, so the boundary test
  passes; values `dmc_v4`/`dmc_v5`). Occurrences:
  [[project_music_assembler_target]], [[project_dmc]].

- **Removal:** at Move 1. The field's permitting condition ("requires more than
  one composer") is false once there is one engine-blind composer, so the
  correct end state is that `_check_origin_engine` can only ever refuse — and
  the field, the validator rule, this entry and the §8 exception all come out
  together. Until then, the count of carriers is a Move-1 progress measure.
