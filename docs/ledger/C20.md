### C20 — Stale-FULL palimpsest (a 'full' row the CURRENT code cannot reproduce)
- **Canonical:** a member's recorded FULL status was earned by an OLDER
  code/verdict combination; the stored artifacts may even still match the orig,
  but re-extracting + rebuilding with CURRENT code yields a partial. The row is
  a PALIMPSEST — it hides the member from every residue census (it never
  appears in a partial cluster) and silently mis-scopes regression claims.
  Occurrences: 0ldsk00l_endtheme (round 9, pre-otrk partial recorded full),
  Happy_Hour (round 16 — exposed the >85-entry track-capacity latent), Yo_Raps
  (stored build diverged at write 0!), Brendas_Got_a_Baby_Mix (round 17 —
  exposed the $175C off-table gap). CANONICAL HANDLING:
  1. When ANY currently-FULL member fails a re-verify, FIRST verify its STORED
     build against the orig. Stored-matches + fresh-fails = a CURRENT-CODE
     latent regression (bisect: USF-diff old vs fresh USF → param-strip bisect
     → divergence-context read); stored-fails = the row was stale — re-bucket
     honestly (tally goes DOWN) and treat the member as a fresh diagnosis.
  2. Attribute before blaming the newest change: the USF diff exonerates or
     convicts extract-side changes in one step.
  3. Periodically re-verify FULL slices with current code (the round-16 727
     sweep found 2 palimpsests); a full-family closeout batch is the complete
     cure.
- **Companion discipline (verify/build code-mismatch):** NEVER mass-write
  artifacts with code that did not produce the verify verdict being trusted —
  a batch's workers import modules at start, so a mid-batch code change (or a
  stashed/popped tree, or committing between verify and write) silently writes
  UNVERIFIED builds recorded as FULL. Re-verify status-changed members with
  the CURRENT tree before mass-writing them.
- **THE "MY FIX REGRESSED N FULLS" TRAP (2026-07-04, round 23 — cost hours,
  TWICE in one session).** When a genuinely-CORRECT shared-code fix appears to
  regress FULL members, the near-universal cause is NOT the fix — it is (a) a
  STALE baseline or (b) a batch flake, and often (c) the "regressed" members
  were FULL through a SUBOPTIMAL path the fix legitimately removes (the user's
  load-bearing insight). Concretely: the round-23 otrk fix "regressed 22 glide
  members + Zak_2 + Bilinski". Reality: all 22 glide members were STALE (a grep
  of stored `.usf` files claimed FULL; CURRENT code builds them partial — I
  compared against `.usf` status, not a fresh build); Zak_2 was a PARALLEL-BATCH
  siddump FLAKE (FULL on a single-threaded re-verify); Bilinski was a stale-full
  palimpsest. NET: 0 real regressions, +12 recoveries. MANDATORY before
  believing ANY regression: re-verify the suspect with a FRESH SINGLE-MEMBER
  current-code build (`find_first_divergence` or a 1-member batch) — never
  against stored `.usf`/DB status, never trust one parallel-batch verdict.
  Corollary: derive a "FULL members" list from a fresh batch, NOT from grepping
  `hvsc85/*.usf` (those are palimpsest-prone).
- **ROOT CAUSE (why palimpsests appeared ~2026-07-03, not before) + STRUCTURAL
  FIX (2026-07-04).** The rapid family-1 rounds switched from *clean full-batch*
  closeouts (jsonl DELETED → every FULL re-earned) to *incremental-merge*
  closeouts for speed (`tmp/merge_r22_reverify.py`: `merged = dict(old)` then
  overlay only the re-verified members → un-touched FULLs keep OLD verdicts
  across code changes). Plus ad-hoc shortcuts that trust persisted artifacts as
  the FULL baseline: `tmp/verify_ondisk_usf.py` (rebuilt from the STORED `.usf`
  → old extract) and `glob hvsc85/*.usf` existence as a "was FULL" proxy. All
  three are the same anti-pattern: a persisted verdict no fresh process
  re-earns. STRUCTURAL FIX: (1) batch results jsonls stamped with a `code_hash`
  (`src/code_fingerprint.py` = hash of the engine's `pipelines/<engine>` +
  `src/usf` + `verify_cycle` dep set); resume reuses a row ONLY on hash match,
  so a code change auto-re-verifies affected members (no "remember to delete the
  jsonl"; parallel-session-safe). (2) `pipelines/<family>/mass_write.py` skip + warn on stale-hash
  FULL rows → never write an unverified `.usf`. (3) the HVSC index dropped ALL
  build-status columns + the `record_*` write-through (2026-07-04) — it's a
  static catalogue now (`hvsc85.parquet`), so it can no longer be a stale-verdict
  surface. Deleted `tmp/verify_ondisk_usf.py`. See [[reference_hvsc_db]].
- **Status:** canonicalized (6 occurrences, 2026-07-02/04, DMC family-1).
- **Consumers:** DMC family-1 rounds 9/16/17/23 handling; the round-16 sweep
  runner `tmp/f1_round16_sweeps.py` (re-verify → then rewrite).
- **Extract-layer relative (C33):** the same "a persisted artifact hides
  reality" shape one level up — a member FULL in regression can have a
  silently-broken REGENERATION/extract path, because regression builds from a
  STORED `.usf`, not from regeneration. A carrier-refactor byte-gate that
  REGENERATES surfaces it (5TT's `unified_inputs` was N `_Inputs` fields
  behind while the member stayed FULL, 2026-07-21). A passing verdict never
  proves the extract still runs. See C33.
- **THIRD LAYER — the stored ARTIFACT itself (schema drift, 2026-07-21).**
  Not a stale verdict (C20) and not a broken extract path (C33): the persisted
  `.usf` becomes UNREADABLE by the current grammar. A typed-field move
  (`speed_ctr_init`, commit 718ade06) orphaned **1,182 of 11,943 stored `.usf`
  files (9.9%)** — 1,098 of them DMC v5. TELL: none. Regression stayed fully
  green throughout, because it builds from a ~116-member portfolio, never from
  the 11,943 stored artifacts. It was found only by accident, while profiling
  something unrelated. What it breaks: `verify_usf` (the production-path
  verdict, which builds FROM a stored `.usf`) and every downstream ML consumer
  — i.e. the corpus the whole project exists to produce.
  - **Detector:** `tools/usf_corpus_check.py` — parses every stored `.usf`
    with the current grammar, groups failures by cause and by DMC family,
    exits 1 on any. ~9 s over 11,943 files. RUN IT AFTER ANY CHANGE TO
    `src/usf/grammar.lark`, `parser.py`, `writer.py` or `types.py`; a schema
    change is not finished until it passes.
  - **Cure:** per owning family, re-run its batch (the `code_hash` gate
    auto-invalidates the affected rows) then its mass-write. Correct scoping
    matters: the f1 mass-write regenerated 5,221 members and fixed *zero* of
    the stale files, because none of them were f1 members — map failures to
    families FIRST (the tool does).
  - **The residue a mass-write can never fix:** members that are not FULL are
    skipped by every mass-write, so a `.usf` left over from when older code
    judged them FULL persists forever. Those are true palimpsests — delete
    them, don't rebuild them.
  - **Trap in the v5 tooling:** `dmc_v5_family_batch.py` writes
    `tmp/dmc_v5_results.jsonl` but `dmc_v5_mass_write.py` defaults to reading
    `tmp/dmc_v5_full_results.jsonl` — a different, legacy file whose rows have
    EMPTY `code_hash`. Running the pair with defaults mass-writes from the
    stale file. Pass `--results` explicitly.

- **FOURTH LAYER (2026-07-21) — the WRITER and the VERIFIER take different
  build paths.** `code_hash` gating proves the verdict was earned by the
  CURRENT CODE; it says nothing about whether the artifact on disk is what
  earned it. DMC's `dmc_mass_write.write_member` built every FULL member
  through the single-player constructor, while `dmc_family_batch.run_member`
  dispatches multi-SID -> compilation -> single. So every multi-SID member
  was stored as a single-chip extraction of a multi-chip tune (a 3-voice
  `.usf` for a 6-voice member), with a perfectly valid `code_hash` beside
  it. NO TELL from any gate: the batch is green, the hash matches, the file
  parses, and regression never reads it.
  - **RULE:** a mass-writer must call the SAME build dispatch as the
    verifier, not a simplified copy of it. When the build path grows a
    branch (a new engine variant, multi-chip, compilations), grep every
    tool that reconstructs a member and add the branch there too — the
    writer is the one that silently disagrees.
  - **DETECTOR:** re-verify from the STORED artifact, not from a fresh
    in-memory build — `verify(orig, <stored>.sidfinity.sid)`. That is the
    only check that exercises writer and verifier against each other.
      Cheap structural smoke for this class: assert an invariant the
    simplified path cannot satisfy (here, a 2SID member's stored `.usf`
    must carry 6 voice blocks and a `sid 2`).
  - Sibling of the third layer: there the stored artifact was unreadable,
    here it is readable, well-formed, `code_hash`-blessed and WRONG.
  - **THE REGRESSION HARNESS IS A CONSUMER TOO (2026-08-22).** The rule was
    written for mass-writers, and `corpus_sync` closed it there — but
    `tools/regression.py`'s DMC worker built EVERY portfolio member through
    `dmc_v4_config(sid)`, i.e. it re-derived (assumed) the single-player
    dispatch. Latent for as long as no portfolio member had another path;
    the 2026-08-22 portfolio re-derivations pulled in two COMPILATIONS
    (Defuzion_3, Nyaaaah_9) and both read as REGRESSED with the textbook
    C31 signature — sub 0 FULL, the rest garbage. Nothing was wrong with
    the composer; the harness was building a different tune. CURE:
    `pipelines.dmc.verify.verify_member(rel)` runs the CANONICAL dispatch
    (2SID / medley / compilation / multiplex / single) and RAISES on a path
    it does not implement, so a future portfolio member of an
    unimplemented path fails LOUDLY instead of silently building as a
    single player. LESSON: enumerate the consumers that reconstruct a
    member — batch, mass-writer, localizer, REGRESSION, and any future
    ML-corpus reader — and make each replay the dispatch rather than
    assume the common case. The dispatch still lives in four places
    (batch worker, `dmc_build_one.build`, `corpus_sync` replay, and now
    `verify_member`); factoring them onto one entry is a Move-1-era
    factor-candidate, and until then each new copy is a place this can
    recur.
  - **CLOSED STRUCTURALLY (2026-07-22), `src/corpus_sync.py`** — shared by
    every family's `pipelines/<family>/mass_write.py`, so a new family inherits it:
    (1) the batch RECORDS `build_path` in its row and the writer REPLAYS it,
    a row missing it refused rather than guessed (`require_build_path`);
    (2) ORPHAN REMOVAL — a non-FULL member must have no stored artifact,
    which nothing else deletes (a mass-write only revisits FULL members, and
    the third layer's detector can't see a file that parses); (3) the writer
    AUDITS a build-path-stratified sample by re-verifying FROM DISK and
    exits non-zero on failure. Only rows matching the current code_hash are
    authoritative for DELETING as well as writing, so a superseded row can
    never remove a live artifact.

## FIFTH LAYER — the stored `.usf` does not REBUILD the stored `.sid`

**(2026-07-22, Nice_Dream_2SID.)** The fourth layer closed "the writer took a
different BUILD PATH than the verifier". This is its sibling: writer and
verifier take the SAME path, but the build consumes a PARAMETER that is not in
the stored `.usf`. DMC's batch has a write-stream RETRY that, for a non-full
member, sets `hold_gateoff='mask_only'` on the parsed USF object and
re-verifies; when that flips the member to FULL the value is recorded in the
batch jsonl, and `dmc_mass_write` re-injected it post-parse when building the
`.sid`. Verdict right, `.sid` right, `.usf` beside them specifying a DIFFERENT
build.

**Why no gate saw it.** Every existing check is satisfied: the batch is green,
the `code_hash` matches, the `.usf` parses, `usf_corpus_check` passes, the
`.usf` is byte-identical to a fresh extract, and the fourth-layer audit
re-verifies the stored `.sid` — which PASSES, because the `.sid` really is
correct. The inconsistency lives strictly BETWEEN the two stored files.

**TELL:** a member reads FULL in the batch but a fresh single-member build
verifies partial, and the numbers are identical across unrelated code changes
(so it is not a flake and not the change under test). Split the layers:
verify the stored `.sid` (passes) -> diff the stored `.usf` vs a fresh extract
(identical) -> rebuild from the stored `.usf` and compare bytes (differs, and
deterministically so across processes — rule out hash-order nondeterminism
first).

**DETECTOR (now wired, ALL families):** `corpus_sync.audit_rebuild(sample,
hvsc_root, build)` asserts, for each sampled member, that
`build(rel, stored .usf) == stored .sid`. This is the general corpus-side form
of the Principle §8 invariant — it catches ANY build input that leaks outside
the USF, not just this one param. It needs no verify signature (only the
family's builder), which is why it lives in `corpus_sync` rather than in each
mass-writer, unlike the verdict audit. `corpus_sync.sample_by_build_path`
stratifies the sample so both audits see the same members and a minority build
path is never skipped. Wired into all three mass-writers (dmc_v4 / fc_standard
/ dmc_v5); FC and v5 were clean when it was added (80/80 and 60/60 sampled
pairs self-consistent), so this is a guard for them, not a fix.

**CURE:** push the retry's value onto the CONFIG so the USF writer emits it
natively, and REFUSE to store the member if it still does not reach the `.usf`.
Do NOT persist it by re-serializing the parsed USF: the USF parse->write
round-trip is not byte-stable (20 of 60 sampled corpus files differ), so
rewriting would churn unrelated text. Root-cause the reason the param was
missing in the first place (here: C9's 5th occurrence — a second constructor
that stopped one layer below where the wedge probes are applied).

### Orphan deletion: a batch may only delete what it OWNS

**(2026-07-22, FC canaries — a self-inflicted break, recorded so it isn't
repeated.)** The orphan rule above ("a member that is NOT full must have no
stored artifact") silently assumes the batch OWNS every member it lists. FC's
batch sweeps every HVSC FutureComposer SID, but `fc_standard_config` refuses
the Tel-variant members with status `flagged` — they are built by their own
canary configs. `plan()` read `flagged` as "not full", orphaned them, and the
sync DELETED `Cybernoid_II` / `Hawkeye` / `Adrenalin`'s stored `.usf` +
`.sidfinity.sid`. The regression then died on a missing file.

Distinguish the two "not full" kinds:

- **NOT MINE** — the extractor REFUSED the member (`flagged`; FC's
  FCStandardUnsupported). Another pipeline owns it. Skip the row entirely:
  neither write nor orphan. `plan(out_of_scope=('flagged',))`.
- **MINE AND FAILED** — the member IS in this family and did not verify
  (`partial` / `error` / DMC's `unsupported`, which means "my member, cannot
  build it"). That IS an orphan.

TELL that a sync is about to do this: the orphan count is small and the paths
are members you recognise as ANOTHER path's canaries. Check `plan().orphans`
before running a sync whose batch sweeps a whole engine FAMILY rather than one
fingerprint cluster.

**A masking interaction made it worse:** before results rows were deduped by
path, a canary usually had BOTH an old `full` row and a new `flagged` row, so
it landed in `write` AND `orphans` — and since `remove_orphans` runs before the
writes, it was deleted and then immediately rewritten. Deduping (last row wins)
removed the accidental rewrite and exposed the latent deletion. A bug that only
survives because two wrongs cancel is still a bug; the fix is the ownership
rule, not the duplication.
- **SIXTH LAYER — NET AGGREGATE COUNTS MASK REGRESSIONS (2026-08-03, r178
  post-mortem).** Between the Jul-22 (r88) and Jul-26 DMC f1 batches, 4
  members regressed full→partial: `cdfa9c42` (the C29 CPU-eye overlay
  generalization, gated on Super_Seven 2/2 + a sample) contaminated the 3
  Flash unpacker members' generated $A2xx data with idle-banking ROM bytes,
  and `d80c1b94` (r116 glide-arrival record creation, gated on Psycho_One)
  broke Tomace/Other_Side via the igla seed. Both batches RECORDED the truth;
  the closeout printed the NET count (+57 full) which masked the −4, the
  partials were folded into the work queue undifferentiated, and the
  alphabetical march — which never revisits a confirmed-FULL — had already
  passed F/T, so the four sat unnoticed until the queue wrapped a week later
  (r176/r177). THE HOLE IS STRUCTURAL, not a bad round: a per-fix census
  gates the fix's KNOWN carriers, the tier-1 portfolio is only as current as
  its last derivation, and the tier-2 batch catches everything — but its
  output was consumed as an aggregate. DETECTOR: `tools/batch_diff.py
  OLD.jsonl NEW.jsonl [--fail-on-regression]` — prints full→partial
  transitions as REGRESSIONS (reproduces the 4 exactly); run it against the
  previous batch at EVERY closeout. A regression is a SIGNAL naming the
  exposure set a fix's census missed — triage it FIRST, separately from the
  pre-existing tail. (Attribution method when one fires: MD5-bisect the
  member's BUILD across the window's commits — byte-identity localizes the
  culprit without verifies; the two culprits here fell in 3 builds each.)

## SEVENTH LAYER — the ORIGINAL changed under the stored artifact

**(2026-08-09, the HVSC #84 -> #85 migration.)** Every layer above is about
OUR side drifting: stale code, wrong build path, a param outside the USF. This
is the mirror — the INPUT drifts. A collection update revises, renames,
re-files and removes originals, and a stored artifact was verified against the
BYTES of one specific original. Nothing binds it to those bytes: `code_hash`
speaks only about our code, `usf_corpus_check` parses the `.usf` happily,
`audit_rebuild` confirms `.usf` -> `.sid`, and regression builds from the
STORED `.usf`, never from the original. So a revised original leaves a
well-formed, self-consistent, code_hash-blessed artifact describing a tune that
no longer exists at that path — and no gate can see it.

**THE IDENTITY TRAP — do not match members by whole-file hash.** The obvious
"which of my members changed" pass hashes the whole `.sid` and calls a path
whose hash moved "changed" and a path that vanished "removed". That is wrong in
the dangerous direction, because the DOMINANT edit in an HVSC update is a
CREDIT/TITLE fix, which changes the PSID header while the music is untouched —
and credit fixes are exactly what drives re-filing (`Andrik/` -> `Duck_LaRock/`,
`Jac/` -> `JAC/`). Whole-file matching therefore reported 47 members "gone",
of which **46 were merely renamed**; under the orphan rule (fourth layer) their
46 valid, verified artifacts would have been DELETED. Only 1 was truly removed.

**Identity across collection versions is the PSID PAYLOAD hash** — md5 of the
bytes after `dataOffset`. It is invariant under every metadata edit and stable
across re-filing, so it answers "is this tune still in the collection, anywhere"
rather than "is this path's file identical". Comparing the three hashes
(header / payload / whole) classifies each member in one pass:

| header | payload | path | action |
|---|---|---|---|
| = | = | same | `carry` — free, no work |
| ≠ | = | same | `reextract_header` — refresh metadata only |
| ≠ | = | moved | `move_reextract_header` |
| = | = | moved | `move` |
| — | ≠ | same | `reextract_data` — artifact genuinely invalid |
| — | absent anywhere | — | `delete` — the only true orphan |

**GATE FOR THE HEADER-ONLY CLASS: byte-identity, not re-verification.** Payload
identical ⇒ the write stream cannot move ⇒ re-verifying with siddump is an
expensive way to learn nothing. Require instead that the rebuilt `.sid` equal
the carried one EXCEPT inside the PSID header. That is strictly stronger and
~100× cheaper (the carrier-refactor discipline, applied to a corpus sync). It
also EARNS ITS KEEP: it caught 36 members whose rebuild differed for an
unrelated reason — their stored artifacts predated current composer code — and
6 more that a v4-only writer refused because they are v5-owned (the "NOT MINE"
case again: an extractor's refusal is evidence about the PATH, never about the
member). Re-verify anything the gate flags before storing it; never leave an
unverified rebuild in place of a verified one.

**A COLLECTION UPDATE ALSO SILENTLY SHRINKS EVERY FAMILY.** Engine
classification (sidid's cached dump) is keyed by HVSC-RELATIVE PATH, so each
re-filed member loses its engine, becomes NULL, and drops out of its family's
batch: DMC 10,676 -> 10,642, FutureComposer 4,024 -> 3,977. Coverage falls with
no gate noticing, because nothing compares family counts across an update.
CHECK FAMILY COUNTS BEFORE AND AFTER. The fix is the same payload identity:
a member whose payload matches one classified in the old tree has byte-identical
player code, so its classification transfers by construction
(`tools/engine_carryover.json`, merged after the dump so a real sidid run wins).

**SIDE EFFECT WORTH PLANNING FOR: renaming the tree invalidates every batch
verdict.** The collection path appears in docstrings inside fingerprinted
engine files, and `code_fingerprint` hashes raw file bytes, so a docstring-only
edit changes the hash — all 5,401 DMC f1 rows went stale at once and the
mass-writer will refuse them until the family is re-batched. Nothing is
*wrong*; it is pure recompute, but it is hours of it, so sequence the rename
with the next planned batch rather than against a fresh one.

Worked instance + the full per-class manifest: `tmp/hvsc85_migration_plan.md`,
`tmp/hvsc85_migrate.py` (plan/apply + verification), `tmp/hvsc85_manifest.json`.

## EIGHTH LAYER — the recorded verdict's VERIFY WINDOW was weaker than ratified (2026-08-11, basic_program)

A verdict can be stale not because code or input drifted but because it was
NEVER MEASURED AT THE RATIFIED STRENGTH: `family_batch._dur` capped every
basic_program verify window at 120 s (`min(songlength*1.1, 120.0)`), so all
>109 s members were recorded FULL on truncated evidence. The full-window
re-verify of the 49 exposed stored members found **44 false FULLs** — ~90%
of the long-tune population. No existing gate could see it: regression, the
mass-write audit, and corpus_check all REUSE the recorded window, so the
false verdicts were self-consistent. It surfaced only when an unrelated
byte-identity gate (the census corpus rewrite) rebuilt one member and its
stored `.sid` mismatched.

TELL: an old batch row whose `len_a` is far below the current orig capture's
write count at the ratified window; any `min()`/cap in a `_dur`-style helper.

CURE: never cap the window (`feedback_subtune_frames_not_arbitrary` is the
law; a cap is the arbitrary-N violation wearing a resource-cost excuse).
When a cap is found: remove it, enumerate the exposure set (every member the
cap could have truncated), re-verify ALL of them at the ratified window, and
expect casualties — re-lift what current code can rescue, orphan-delete the
rest per corpus-sync.

SECOND-ORDER FINDING the re-measure forced: the window derives from the
SONGLENGTH DATABASE, and for RSID-BASIC members SLDB itself is broken by the
BASIC precalc dead-air (America_the_Beautiful's entry covered ONLY its 114 s
delay; 31 of the 44 needed measured `tools/songlength_overrides.json`
corrections; 13 loopers keep the SLDB cut). Measure first gate-on + last
write over a generous capture before trusting any entry a verdict depends on.

## NINTH LAYER — the INVALIDATION FUNCTION itself is under-inclusive (2026-08-22)

Every layer above assumes the code_hash gate answers "is this row current?"
correctly. It is a hand-declared, unenforced dependency set, and it was wrong
in both directions at once. Rothermel & Harrold's axes split the two, and only
one of them can produce a wrong answer:

- **PRECISION failure** (set too BROAD) — re-verification we did not need.
  Costs compute; CANNOT produce a wrong verdict. `dmc_v4` declared the whole
  `pipelines/dmc` tree, so one edit to a v5 file invalidated 8,369 v4 rows.
- **INCLUSIVENESS / safety failure** (set too NARROW) — a cached FULL that
  current code cannot reproduce. SILENTLY WRONG, and undetectable by every
  other layer. This is the ninth layer.

THREE MEASURED HOLES, all closed in 4f46e7af:

1. **The toolchain was not hashed at all.** `tools/siddump` sits on BOTH SIDES
   of the comparison — it produces the REFERENCE trace too. Rebuild it, or
   relink against a different libsidplayfp, and ground truth moves with nothing
   invalidated. (Bazel documents this verbatim as a known remote-caching issue;
   ccache treats hashing the compiler as non-negotiable; REAPI requires tools
   inside the input root; SLSA L3 requires pin-by-digest.) Same for `xa65`,
   which assembles the bytes we then measure.
2. **The file filter globbed `*.py` only** — so `pipelines/dmc/docs/*.bin`, the
   CANON PLAYER BINARIES the factory dispatches and probes against, were
   unhashed while sitting INSIDE a declared directory. Cure: an inert-suffix
   denylist, so a new file TYPE is hashed by default.
3. **Verdict inputs were absent**: `src/composer_runtime/` (it emits the
   bytes), `src/songlengths.py` + `songlength_overrides.json` (the verify
   WINDOW — the eighth layer above was exactly a window change), the USF
   grammar, `seed_disassembly.parse_psid`, the py65 interpreter that runs
   extraction probes, and `lark` itself (an unpinned third-party package).

CURE — DERIVE THE SET, DON'T DECLARE IT (`tools/derive_deps.py`): snapshot
`sys.modules` after real work, per (engine, CONSUMER), and hash exactly that.
It captures function-local imports by construction — `composer_v5` imports
`pipelines/dmc/composer_asm._sanitize_asm` inside a function, which no static
walk can see.

FOUR TRAPS IN DOING THIS, all hit:

- **THE CLOSURE IS PER-CONSUMER, NOT PER-ENGINE.** The DMC batch worker loads
  55 repo modules; the regression harness's `verify_member` path loads 57 and
  includes `pipelines/dmc/verify.py`, which the batch never touches.
- **A CLOSURE MEASURED ON ONE MEMBER UNDER-APPROXIMATES** — the unsafe
  direction. DMC f1's `single` path loads 56 modules, `hetero_masm` 68,
  `hetero_v5` 76; the union over its 7 build paths is 77. Stratify over
  `build_path` and take the UNION, or silently under-hash by ~20 files.
- **A DERIVATION THAT "RAN AND PRODUCED NUMBERS" MAY HAVE MEASURED NOTHING.**
  The first run returned a plausible, uniform 61 modules for every member
  because `_worker_init()` had not run, so `run_member` raised on its first use
  in ~0.3 s. A derivation tool must report each member's VERDICT STATUS and
  refuse a sample where nothing reached one.
- **THE KEY WAS SELF-INVALIDATING.** Batches import `src/code_fingerprint.py`
  to compute the key, so the derived closure captured it — and then every edit
  to the hashing logic invalidated every verdict everywhere, including edits
  that only WIDEN coverage. Excluded by name; it cannot affect a verdict.

FAMILIES ARE NOT INDEPENDENT, AND DERIVATION IS WHAT PROVES IT. The tempting
goal was "a v5 edit must stop invalidating v4". Measured, that is FALSE: f1's
`hetero_v5` build path runs a real v5 sub-player and `hetero_masm` runs the
whole Music_Assembler pipeline, so v4's closure legitimately contains 7 v5
files and 11 MA files. The right criterion is **"a file used by only one
consumer must move only that consumer's key"**, not "families must be
independent".

MIGRATING ACROSS A KEY CHANGE (`tools/migrate_verdict_rows.py`): folding new
inputs in invalidates everything although no INPUT moved. Restamp only under
proof — for each file in the NEW closure, did its CONTENT change since the rows
were stamped? Use `git diff <commit-at-stamp-time>`, never mtime: a file
modified and restored byte-identically has a fresh mtime, and the first
mtime-based cut refused all six families on artifacts of the session's own
probes. Untracked inputs (built toolchain, `.pylocal`) have no such record —
report them separately and require an explicit accept-with-reason recorded in
the row.

**4th-layer occurrence, the ROUTER as the mis-dispatching consumer
(2026-08-28, Nice_Dream_2SID):** `route()` probed only the single-player
`dmc_v4_config`; base detection landed on chip 2's player and the chipless
compare refused a normal chip-2 `$D42x` relocation — while the batch, which
dispatches `dmc_v4_config_2sid` first, had verified the member FULL. The
roster then claimed it for nobody, and the stored artifacts became a
palimpsest nothing would revisit (surfaced by `route.py --gaps`'s mirror
check). The rule generalizes: a ROUTER/claim probe is a consumer too, and it
must probe the same dispatch paths the batch does.

## TENTH LAYER — PROVE the staleness is NOMINAL instead of re-batching
## (2026-08-31)

Every layer above is about a stored verdict the current code cannot
reproduce. This layer is the mirror: a verdict the current code reproduces
EXACTLY, marked stale anyway.

`code_fingerprint` hashes content and cannot know semantics, so a
byte-neutral edit — a schema addition elided at its default, a directory move
with path fixups — marks whole families stale. That is the SAFE direction and
must stay the default (a precision failure costs compute; the other direction
is silently wrong). But it presents to the owner as "re-verify 8,000+ members",
and the honest question is whether anything actually moved.

MEASURE IT, do not assume it either way. Rebuild a stratified sample FROM THE
STORED `.usf` under current code and compare to the stored `.sid`
(`tools/verdict_staleness_probe.py`). Byte-identical ⇒ identical write
stream ⇒ identical verdict — a STRONGER statement than re-verification and
~100x cheaper (the CLAUDE.md carrier-refactor gate, applied to staleness).

Worked, 2026-08-29→31 (the digi schema landing moved `src/usf/*`):

    spot check   dmc_v4 191/191 byte-identical over ALL SEVEN build paths,
                 dmc_v5 60/60, fc_standard 60/60
    then the     dmc_v5 re-batched IN FULL: 2,078 members, 1h42m
    expensive    1211 full / 867 partial before AND after,
    confirmation 0 status changes member-by-member,
                 0 partials whose first-divergence signature moved
    and 3 more   basic_program 524/524, goattracker_v1 1387/1387,
    families     fc_standard 4093/4093 — all 0 changes

8,082 members re-verified, not one changed. The prediction from a 311-member
byte-identity sample held exactly at the verdict level on whole families.

⚠ BOUNDARIES. It proves nothing about members with NO stored artifact
(non-FULL ones — they get re-verified regardless), and nothing about a family
with no mass-write (music_assembler / goattracker_v1 store nothing). And
`migrate_verdict_rows` cannot express this proof today: it refuses on git
CONTENT change and has no byte-identity mode. Adding one
(`--prove-by-rebuild N`) is a change to the RESTAMP PROOF and therefore owner
territory — see backlog 31.

⚠ STRATIFY OVER `build_path`. A family that dispatches several paths can be
unchanged on one and broken on another (the fourth layer above); the dmc_v4
sample deliberately covered all seven.
