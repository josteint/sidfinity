### C8 — A de-fused per-entity program pool overflows the engine's byte index
- **Canonical:** the engine stores N programs in one table indexed by a single
  byte (position ≤ 255); the composer emits a SEPARATE copy per entity, so a
  member with many same-shape entities inflates the pool past 255 → hard build
  error. **Dedup identical programs** (key on the exact emitted bytes + loop):
  identical entities point at one pooled copy. Byte-identical for the write
  stream — each entity re-inits its position to its start per use and reads the
  same byte sequence. This is what the original packer does (programs share).
- **Status:** canonicalized ≥2× (DMC v4 wave pool 2026-06-25; DMC v5 wave pool
  2026-07-01).
- **Sibling — dedup KEY excludes a reachability artifact (2026-07-10, Balloonacy
  compilation instrument pool, C31):** the overflowing pool is the 28-inst
  5-bit id cap of a merged compilation. Two instruments identical but for
  `offtable_freq` (a C6 which-notes-played artifact, NOT intrinsic content) are
  ONE instrument — dedup on all fields EXCEPT offtable_freq and carry the UNION
  of records (collision → refuse). Same lesson as the base entry (share what the
  packer shares), applied to the DEDUP KEY: exclude non-intrinsic fields so
  behaviorally-identical entities collapse. See C31 for detail.
- **Sibling instance (capacity of a COMPOSER-side stream index, 2026-07-03):**
  when the overflowing index is the composer's OWN runtime cursor (not a pooled
  table) — e.g. the DMC track stream growing past 255 bytes once entries went
  2→3 bytes — dedup doesn't apply; WIDEN the cursor to a 16-bit running pointer
  and emit jump targets as assembler label arithmetic (`.byt $FF, <(lbl+n*3),
  >(lbl+n*3)`). Audit every 8-bit index whenever a stride/record grows.
- **Boundary:** dedup is pure packing (zero write-stream change) ONLY when the
  pool layout is position-INDEPENDENT — i.e. the loop marker is RELATIVE (V4's
  `$90 + n - loop`, identical bytes at any position). When the marker encodes an
  ABSOLUTE target (V5's `$90, s+loop`), moving a program rewrites its marker and
  dedup is NOT guaranteed byte-identical: it perturbed a currently-FULL member
  (CreaMD Ambient, freq divergence — the de-fusion adjacency coupling the pulse
  table also shows). Fix = OVERFLOW-GATE the dedup (share only when the un-shared
  pool > 256), which is zero-regression BY CONSTRUCTION: it only ever touches
  members that can't build un-shared (all currently non-FULL), so no working
  member changes. **SUFFIX/OVERLAP packing is REFUTED as the next tier (2026-07-01,
  `tmp/measure_suffix_overlap.py`):** measured on the DMC v5 family-4 pulse-overflow
  members, suffix-containment AND greedy shortest-common-superstring add essentially
  NOTHING over identical-dedup (e.g. Deep_Acid 346→346, Speed_Biker 306→305; 2/10 fit).
  REASON: each program is captured as a SEPARATE SweepEnvelope with its START value
  PREPENDED to its phases; in the ORIGINAL shared table a program's start is just a
  position that ALSO serves as another program's phase byte (start+phases overlap), but
  the un-fused capture puts a distinct start (a PW value) in front of each phase list, so
  the sequences don't share suffixes even when the programs walk the same table. The
  engine's compactness IS the shared table — packing the separate captures can't recover
  it. **The real next tier is EMIT-AND-WALK the shared static table** (emit the 256-entry
  m.pulse/filter once, point each instrument's pulse_ptr/filter_ptr into it, like the
  engine) — fits by construction (256 positions = the byte pointer's range) but is a
  representation change, not a packing tweak. Deferred (bigger architectural
  change). [2026-08-26: the overflow residue (126 members by then) was instead
  unblocked by the SIXTH widening below — paging the composer's own cursor,
  no representation change.]
- **FIRST ASK WHOSE CAP IT IS (2026-07-22, Heavy_Metal_Deluxe_beta, DMC f1
  compilation instrument pool).** Before packing harder to fit a cap, check
  that the cap is OUR ENGINE'S and not the ORIGINAL FORMAT'S. The merged
  instrument pool refused >28 because DMC's editor selects an instrument with
  a 5-bit `$60+id` row field — but the composer emits its OWN pattern encoding
  (parallel arrays; the slot rides a full operand byte), so that field binds
  nothing in the rebuild. The constant had been transcribed from the disasm,
  not measured. The composer's REAL cap is its own widest id-scaled index —
  here fx_pulse's `lda cinst,x / asl×3 / adc pwphase,x / tay`, 8-bit at stride
  8 ⇒ 32 instruments. Raising it to the measured bound landed a member at 30
  with no other change (3/3 FULL). TELL: a capacity constant whose comment
  cites the ORIGINAL's bit-field width. METHOD: grep every table the id
  scales, take the min bound, and name the audited chain in the comment.
  Zero-regression BY CONSTRUCTION when overflow FALLS BACK to another build
  path (only members that already fail can change path — the same argument as
  the overflow-gated dedup above; census the fallback set to prove it).
  **Then, past the real bound, WIDEN it (2026-07-22, Lane_Crazy, 39
  instruments — the same day, the very next member).** Raising the constant is
  only step one; the index behind it is the actual object. Here the wrap was
  silent-but-audible: ids ≥32 aliased onto instrument 0's records and the
  member diverged at V1 PW lo, write 24 — the TELL that a capacity constant
  was raised past its index rather than with it. The widening that fits this
  family of cases is NOT a 16-bit index: shrink the STRIDE to the record's
  true width and give each entity a base BYTE (`ldy id,x / lda base,y / adc
  phase,x`), which keeps the index 8-bit, costs one cycle LESS than the shift
  chain it replaces, and moves the cap to 256/stride (here 8→6, so 32→42).
  A stride is often padded to a power of two only so the index can be a shift;
  that padding is what you spend. GATE on the count so everything below the
  old bound emits byte-identical code — then the gate's proof is a corpus-wide
  MD5 rebuild (5240/5240 identical), not re-verification. REFUSE, don't
  approximate, where another feature encodes POSITIONS in the old layout (the
  dual_freq_generator wedge reads off the end of a stride-8 record; there is no
  compact-layout form, and the intersection is empty today).
  ⚠ Neither side of a lineage necessarily has the wider index: DMC's ORIGINAL
  computes its record offset as ASL×3 + ADC×3 (=×11) in the 8-bit accumulator
  with carries dropped, wrapping after 23 instruments — INSIDE the editor's own
  0-27 range (the C11 wrap). The original never needs more because one editor
  file holds ≤28; the overflow exists only because the MERGE of N packed
  players creates an entity count the original format never faces. So don't go
  looking for the original's answer — it doesn't have one.
- **Sixth widening — PAGED composer pools (2026-08-26, backlog item 19
  option (c) — the whole v5 table-overflow bucket unblocked).** Past
  identical-program dedup, the v5 de-fused pulse/filter/wave pools still
  reach 981 entries (medians ~400 — packing cannot help; suffix/overlap
  packing was REFUTED above, and the emit-and-walk alternative is a schema
  addition parked with the owner). The 256 cap is OUR composer's own 8-bit
  cursor (`ldy pulsepos,x / lda pulsehi,y`), NOT the format's — the Core
  Tenet licenses widening it with nothing added to the USF. Shape (all
  gated on `len(pool) > 256`, so every fitting member is byte-identical —
  proven 60/60 MD5 vs HEAD incl. every family-4 portfolio member):
  * `from_usf` pass-2 packer: same programs laid out page-padded — a
    program (incl. its `$90` marker) never straddles a 256-byte page, so
    the engine's 8-bit position stays a valid IN-PAGE offset and the `$90`
    marker's `& $FF` target stays correct; pulse/filter programs never
    start at in-page offset 0 (the engine reads the ptr low byte as its
    "restart?" flag). Per-instrument page triples ride `m.instr_pages`.
  * composer: page-aligns the six arrays (`.dsb (256-(*&255))&255`), emits
    a stride-8 `instpg` page table (indexed by the same `instr_n*8` Y as
    the record), and SMC-patches every read site's operand HI byte with
    `page + >array` — at note_init2 (new instrument, while Y holds the
    record index) and at each steady block's entry (eff_steady /
    wave_step / filter_run) from per-voice `wavepg,x`/`pulsepg,x`
    (`filterpos` is global + V3-only → one `filtpg` byte, set only when a
    program is SET). The page registers live in the cleared state block,
    so a re-init lands on page 0 and the entry stubs re-patch before any
    read. ~60-90 cycles/play — 0.4% of a vblank budget (C25 satisfied;
    tightest overflow-member CIA latch 4,913 → ~2%).
  * ⚠ THE PAGE NUMBER IS NOT THE OPERAND HI BYTE. The first cut stored the
    raw page (0..3) into the operand — every patched read pointed at
    $00xx-$03xx and members diverged at the lead-in. The patch value is
    `>array + page`, one add per ARRAY group (wavectrl vs wavefreq etc.
    have different bases; a single per-pool value cannot serve both).
  * REFUSED, not approximated (this entry's rule): members whose off-table
    freq read sonifies the LIVE pulsepos/filterpos (family-correct state
    windows — f3 base+$7F6-$7F9, f4 base+$800-$803). The refusal fires AT
    THE EXTRACT BOUNDARY (`write_v5_usf` raises `unsupported:
    offtable_live_pos` before any .usf exists), pairing the extract's
    live-window fact with `from_usf.defused_pool_overflow` — a size-only
    mirror of the packer that `usf_to_model` asserts against its real
    pools on every build (drift tripwire). The capture-validity fact
    deliberately never enters the USF: a first cut carried it as a params
    key, which was a non-musical marker riding the schema — reverted the
    same day (the USF carries music; extract-side judgments raise
    extract-side). Census 2026-08-26: exactly 4 of 126 (all family-4). NB
    the item-19 de-risk census said 6 — it applied the family-3 window to
    family-4 members, where $17F6-$17F9 is glide state, not positions; the
    2 misflagged members build honestly. SAME-DAY RESOLUTION (two steps):
    first the C11 read-moment ladder narrowed 4 -> 2; then the
    LIVE-POSITION FORM (owner-approved: OFSIG `pulse_position`/
    `filter_position` + per-instrument `pulse_table_pos`/`filter_table_pos`
    + the composer's delta-serve redirect — see C11's 2026-08-26
    refinement) EMPTIED the class: all 4 build, refusal reserved for reads
    observed outside a captured program region (none known).
  * Validation trick worth keeping: `from_usf._FORCE_PAGED` runs the paged
    packer on FITTING members — force-paged verify of 6 diverse FULLs
    (incl. family-4 + live-pos carriers) stayed 6/6 FULL, separating
    "machinery broken" from "overflow members carry other residue".

- **Third widening — the POOLED pulse-step layout (2026-08-04, r180,
  Lane_Crazy → family-1 100%).** Above 42 instruments even the compact
  stride-6 layout overflows the 8-bit index (42*6+5 = 255). The composer now
  DEDUPS identical 6-byte step blocks into a pool; `istepbase` becomes a
  per-instrument POINTER into it, so capacity is DISTINCT-BLOCKS-bounded
  (≤ 42 blocks) with the instrument count free to 255 (cinst is a byte).
  Triple-gated per the C8 gate pattern — ≤32 stride-8, 33-42 dense stride-6,
  43+ pooled — proven byte-identical for 31 members vs the pre-change stored
  corpus. The merge-side cap (`_place` in compilation.py) mirrors it
  block-aware (distinct padded speed_steps tuples ≤ 42, instruments ≤ 255).
  Next widening if ever needed: a 16-bit index (C25 cycle-cost caution).
  NB the capacity pressure itself was largely OVER-SPLITTING, not content —
  see the C31 behavioral-identity note (position rides instrument identity
  only when a read can observe it); widen only AFTER that dedup is applied.
- **Fourth widening — the SUBTUNE record index (2026-08-19, Session subs
  16-24 FULL).** The unified composer's init fetches its stride-16 tune
  records with `subtune*16` (ASL×4) in 8-bit Y — wraps at 17+ subtunes
  (16*16 = 256 → 0), so every subtune ≥16 silently played subtune-16's
  record: wrong track pointers, speed, mvol, shadow17 and the per-subtune
  knob bytes, presenting as "state_match=False + wrong first note/instrument
  at play position 0" across a whole block of subtunes. Merge-created like
  the instrument-offset sibling above: the orig packs N small stride-8
  tables (5 records each — no wrap anywhere); the single 25-record table is
  ours. CURE: keep Y as the record LO byte and have init SMC-patch each
  tunetab read's operand HI byte with the record page (`subtune >> 4`,
  computed once into `tmp`, `clc/adc/sta site+2` per labeled read site
  ttp0-ttp7 incl. the conditional per-subtune knob loads) — gated on
  `len(subtunes) > 16` so every ≤16-subtune member emits byte-identically
  (golden 8/8 MD5 incl. per-sub-knob carriers + the medley; full regression
  green). Corpus carriers: exactly 2 headers >16 subs (Session 25;
  Arc_Doors 20, unmigrated). TELL: a compilation whose failing subtunes are
  exactly those ≥16, each playing subtune (k-16)'s music — diff the
  rebuild's own subtunes against each other before suspecting the merge.
  SIBLING, same member, same day: the per-subtune off-table WINDOW patch
  stream (`ovrbase`/`ovrpat`, the C31 window-conflict machinery) had an
  8-bit guard that silently DROPPED the whole patch when
  `subtunes*(2*conflicts+1) > 256` (Session: 6 conflicts × 25 rows = 325)
  — so subtune 6's glide-arrival byte (window pos 1 = idx 97, a
  per-context value) was served the static last-wins window and the
  slide-form glide NEVER ARRIVED (orig snaps to the off-table-served base;
  the rebuild extrapolates past the target). CURE: a WIDE form — 16-bit
  per-subtune row bases emitted as label arithmetic (`.byt <(ovrpat+b)…`),
  init SMC-patches both stream reads, Y walks the row from 0 (a row > 255
  still drops). LESSON: when one member overflows ONE composer 8-bit
  index, audit the member's OTHER per-subtune 8-bit streams the same day —
  the same count drives them all (the fpat tuning / vpat vibdepth guards
  keep their drop behavior; no carrier yet).
- **Fifth widening — the merged WAVE POOL (2026-08-21, Comer/Artris 6/6
  FULL):** a 2-player compilation merge pooled 332 deduped wave-program
  bytes over 42 instruments — past the 8-bit `wavepos` capacity although
  each PLAYER's own pool fits (the C8 signature: the overflow is created
  by our merge; the original has two separate ≤255 pools). Cure per the
  fourth widening's SMC pattern, but SPLIT instead of widened: each
  subtune runs exactly one player (C31), so the subtunes partition into
  components sharing no instruments — `_Model._split_wave_pools` pools

  wavepos walks the right lead-in; a per-subtune idle override becomes its

  wave-step read operands (`wsp0-3` → `wplotab/wphitab/wfplotab/wfphitab`
  indexed by `wpooltab[cursong]`, both directions on every init). Fires
  ONLY where the single pool overflows — previously a hard build error, so
  no existing member can regress; refuses (assert stands) when subtunes
