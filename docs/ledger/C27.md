### C27 — Multi-SID (2SID/3SID): N independent players, one per chip

- **Problem shape:** a member declares 2/3 SID chips (PSID v3/v4 header
  +$7A/+$7B) and its play vector is a dispatch WRAPPER calling two/three
  complete sub-players, each writing a different chip ($D400 / $D420 /
  $D440). The player families are otherwise ordinary (DMC 2entry here). One
  sub-player's jump table is often overwritten by the wrapper.
- **Decomposition (the key insight):** a multi-SID tune = N independent
  single-chip tunes playing simultaneously. Because the wrapper runs the
  players SEQUENTIALLY (JSR p1; JSR p2), the merged write-log per frame =
  [p1's chip-1 stream][p2's chip-2 stream] — so each sub-player is extracted
  + composed + verified with the EXISTING single-chip machinery, only
  chip-TAGGED.
- **Verify:** siddump logs every installed chip, merged into one
  cycle-ordered stream with reg encoded `chip*$20 + reg`; single-chip output
  is byte-identical, so all flat `(reg,val)` comparators work unchanged.
- **USF:** voices number THROUGH the chips (1-3 = chip 1, 4-6 = chip 2, ...);
  chip count derives from the voice-block count; per-chip tempo/global/init
  ride optional `tempo N`/`global N`/`sid N` forms; the extra chips' SID
  MODELS ride `psid.sid2/sid3` (only when the header states one). Chip I/O
  ADDRESSES are NOT in USF — they are pipeline constants (chip 2 = $D420,
  chip 3 = $D440), the I/O-space analogue of "the composer always emits the
  player at $1000" (they'd be opaque hardware tokens hurting ML). Merge
  gives each chip's instruments + filter window a fixed-stride disjoint id
  block so the composer's split inverts it exactly (each chip's sub-USF ==
  its standalone extraction).
- **Compose:** one clean player instance per chip (own origin; chip k>0
  writes $D400+k*$20 via a register-operand relocation) + a dispatcher whose
  init/play call each in turn. Per-instance write-stream QUIRKS are config,
  not mechanism (Nice_Dream: the res/route $D417 write is left on chip 1 for
  BOTH players — an editor relocation quirk, reproduced by keeping $D417
  un-relocated).
- **REFINEMENT (2026-07-21) — a subtune need not sound every chip, and the
  wrapper picks each chip's SONG.** The "N independent tunes playing
  simultaneously" decomposition holds per SUBTUNE, not per file. Rayden's 7
  2SID builds ship subtune 0 = both chips, 1 = chip 1 only, 2 = chip 2 only,
  by SMC-patching the four call opcodes `$20` (JSR) ↔ `$2C` (BIT); and they
  hardcode `LDA #$00` before BOTH player inits, so each chip always plays its
  OWN song 0 regardless of the PSID subtune — the multi-SID form of C31's
  per-subtune (player, song) map (distinct from C31 proper: same players
  throughout, only gated). Both facts are OBSERVED under py65 per C18
  (`factory.multisid_active_chips` records which player regions the PC enters
  and the A each player's init is entered with; the image is reloaded per
  subtune because the gating is SMC) — never parsed. Representation needs NO
  new field: a chip sounds in a subtune iff the subtune carries its VOICES, so
  a chip-2-only subtune is simply voices 4-6 (the USF parser's "numbered
  1..3N consecutively" rule was relaxed to whole ascending 3-voice chip
  blocks). Per-chip `tempo N`/`sid N` are omitted for a chip that does not
  sound; the base tempo is the first SOUNDING chip's. The composer derives
  n_chips from the highest voice id, gates each chip's init+play on a
  per-subtune activity byte (clean gated calls, NOT the orig's SMC — core
  tenet), and gives a non-sounding chip a stopped placeholder song so
  A=subtune stays aligned.
- **A SUB-PLAYER IS AN ORDINARY PLAYER — build it through the ordinary path
  (2026-07-21).** The per-chip constructor hand-rolled a config (addresses
  only), so every knob the canonical build probes was silently defaulted —
  see C9's 4th occurrence for the general lesson. Route it through the
  canonical build with the base forced (the C31 compilation mechanism),
  keeping the hand-rolled config as a fallback for a player whose jump table
  the wrapper clobbered. Two things must generalise first, both because a
  chip-2 player is chip 1's player COPIED WITH PER-CHIP RELOCATIONS:
  (a) the masked identity compare must tolerate a `$D4xx` store operand
  moved to this chip's address — mask those two bytes only where the
  member's operand is the canon register or its chip-relocated twin, so a
  real wedge still fails; (b) any probe keyed on an engine-internal
  CONSTANT must key on the SHAPE instead — the track-loop hook probe matched
  the zeropage track pointer `$F8`, but chip 2 gets its own zp pair (two
  players cannot share one). Ask of every probe: is this byte per-CHIP?
- **PER-CHIP PARAMS ARE A CLASS, not one key.** Anything describing the
  WRAPPER's treatment of one chip's player is per-chip and merges as a
  ';'-separated list in chip order: `multisid_keep_regs` (C19) AND the C18
  `play_phases`/`noteinit_deferred`. A wrapper may run ONE chip per call
  (`INC ctr / AND #$01 / BEQ ; JMP chip2 ; JMP chip1`), so the chips observe
  COMPLEMENTARY schedules (`P_S` / `S_P`) and each ticks at half the timer
  rate — a legitimate disagreement, which the "chips must agree" assert
  (below) would otherwise read as a non-first-chip wedge. Accept an 'S'
  phase (normally refused: under py65 an S usually means an IRQ-armed
  effects call did not run) ONLY on the structural evidence — same period
  across chips, exactly one chip non-S at every index. A py65 shortfall
  cannot fake that: it hits every chip at the same index, leaving all S.
- **TRAP — the merge drops non-first chips' params.** `merge_2sid_usf` built
  the result from `usfs[0]`, silently discarding every other chip's params:
  the per-voice otrk phase scalars AND any C19 wedge on chip 2. Params split
  three ways: per-chip by construction (`multisid_keep_regs`), PER-VOICE
  (`..._v<N>` — renumber with the voice, exactly like the voice blocks), and
  player-wide (must AGREE across chips — the chips are copies of one player,
  so a disagreement means a non-first-chip wedge and must fail loudly).
- **DETECTION — three traps, all cured by OBSERVING (2026-07-21).** (a) The
  wrapper scan must accept a NEUTERED call (`$2C` BIT as well as `$20` JSR):
  the gating patches that opcode per subtune, so a member saved under a
  chip-only subtune ships it as BIT, and it still NAMES its player (C19
  save-moment). (b) NEVER identify a chip by an ADDRESS RANGE — players sit
  less than a page apart and the dispatch wrapper can lie inside a player's
  nominal page, so ranges overlap each other AND swallow the wrapper; watch
  each player's own ENTRY VECTORS (base, base+3, or the direct 2entry handler
  at base+$50). (c) A C18 PHASE CYCLER can sit in FRONT of the per-chip calls,
  so the scan sees `LDA #imm` where it expects a call — fall back to
  DISCOVERING the bases by running init under py65 and collecting JSR targets
  shaped like a 2-entry jump table (page-aligned, JMP at +0 and +3). Observe
  the schedule PER CHIP (the shared single-chip observer's pc-trace fallback
  cannot disentangle two players in one trace); the composer's phase
  dispatcher lives inside each player, so the chips cycle in lockstep with no
  dispatcher change. (d) The wrapper need not use JSR at all: a play VECTOR
  that is itself the phase cycler (not `JMP wrapper`) must be scanned from
  the vector, an out-of-image play (== 0 — the tune installs its own IRQ)
  has nothing to scan, and an init that TAIL-JUMPS into chip 2's init
  (`JSR chip1init / LDA #$00 / JMP chip2init`) is reached only if the
  observer accepts JMP targets. Add the looser scan as a RETRY after the
  JSR-only pass, never in place of it — a member the strict pass already
  resolves then cannot be pushed over the chip count. (e) The wrapper may
  pick the player by SMC-patching its OWN call operand per call, so chip 2
  is never named during init — run a few PLAY calls too, and read the
  operand at EXECUTION time (that is the whole point; parsing cannot work).
  (f) Test the jump-table signature against LIVE memory, not the file image:
  an init can COPY a player to its run address (Mothafucka relocates chip 2
  to `$E800`, zero-fill in the file — C26 applied to the player itself).
  RELOCATING WRAPPER (C31 applied to a multi-SID member): the init copies
  players AND SONG DATA into RAM, so a chip whose player is IN the image can
  still have its SECTORS out of it — Mothafucka's chip 1 player sits at $1000
  but its sectors are copied to $8000+ (out of the $0900-$4FB8 image, zero-
  fill there), so reading the raw image decodes them as garbage rows (a
  constant wrong-instrument note). CURE: when ANY chip's player is out of the
  image (the tell that init relocates), extract EVERY chip from POST-INIT RAM
  — `dmc_v4_config_2sid` snapshots the file's start-song landing (the copy
  runs at init before any per-subtune call gating) and threads that view
  through `_config_at_base(post_init_sub=)` into `_build_via_canon` + the
  wedge probes + `_multisid_keep_regs` (every layer that reads memory for the
  chip). When every player is in the image (the common 2SID build), the raw
  image is used (`post_init_sub=None`), byte-identical to before. A chip that
  is neither a valid in-image player NOR materialised in post-init RAM is
  still refused (fall back to the single-chip build; never raise mid-extract).
  No FULL member can regress: an out-of-image chip was refused → single →
  partial before, so it can only improve.

- **TWO PLAYERS ON ONE CHIP, TIME-MULTIPLEXED (2026-08-14, Moog/Techno-Rap
  — the "complementary schedule" form without a second chip):** the file
  packs two INDEPENDENT f2 tunes; a CIA at ~100 Hz (2× the frame) drives a
  wrapper that alternates them via a zp parity, so each tune runs at ~50 Hz
  and BOTH write $D400-$D418. Diagnosis = split the per-IRQ capture by
  parity: each half is internally coherent and musically DIFFERENT (one
  holds a note with a PWM sweep + active filter + $D418=$1F; the other
  plays noise and never sets the filter). Our single-player build
  reproduces its half EXACTLY — every apparent mismatch was the per-IRQ
  capture STRADDLE (a burst overruns the next IRQ; the truncated chunk's
  tail opens the following chunk), so the whole gap is "the second player
  is missing", not an extraction defect.
  ⚠ **DO NOT collapse the two bursts into one frame.** It is the tempting
  fix (the flat stream matches byte-for-byte and the verdict says FULL),
  but measurement kills it: the bursts are ~4% of a frame each and sit
  50.2% of a frame APART, so bunching them shifts one whole tune half a
  frame (~10 ms) against the other — audible, and INVISIBLE to the flat
  verdict. This is the worked example behind the Trap B BOUNDARY now
  recorded in `docs/the_core_tenet.md` (intra-frame position is signal
  when the original spreads work across sub-frame IRQs). Reproduce the
  100 Hz pacing with our OWN dispatcher (no zp flag, no SMC — core tenet)
  and complementary per-call schedules, exactly as the multi-SID
  `P_S`/`S_P` form above, but with reg_delta 0 and a 1-chip header so the
  verdict compares the merged stream strictly (C28 does NOT split).
  Extraction blocker seen: the second player's data-table operands are
  INDEPENDENTLY packer-patched (+$C00 / +$C02 / +$BFE / +$BB0 — resolve by
  operand, never a fixed offset) and its filter-def operand is a
  relocation MISS pointing OUT OF THE IMAGE (+$4004), which trips
  `layout_disorder_f2` even though the tune never audibly uses the filter.
  Occurrences in [[project_dmc]].
