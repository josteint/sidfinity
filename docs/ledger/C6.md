### C6 — Off-table FREQ-table lookup (index past the N-entry freq table)
- **Canonical (CANONICALIZED 2026-06-21, both consumers):** when a melodic/effect
  path adds a table-relative offset to a note and the 8-bit index
  `(offset + note) & $FF` passes the freq table, the read falls into the following
  image bytes, which the orig plays as REAL freqs (content-by-reference, not a bug
  to clamp). **Deconstruct each off-table read to a musical FREQUENCY attributed to
  the instrument + note that plays it** — per-instrument `Instrument.offtable_freq`
  records `(offset, note, lo, hi)`, idx=(offset+note)&$FF (the ML learns a
  drum/tone pitch, not a byte at a memory offset). The composer rebuilds whatever
  internal window/layout it needs FROM those records (engine-blind); the USF never
  carries the opaque window. This is C7-option-(a) realized. ❌ DO NOT emit a
  contiguous `freq_overrun` window — that is the superseded form (it silently masks
  reach-model under-captures within its span; see the LO-read bug below).
- **Status:** `canonical` (FC standard + DMC v5 + GoatTracker V1, all migrated to
  `offtable_freq`). Schema + USF I/O shared; the composer reconstruction is per-composer
  (FC `composer_asm._offtable_window` · v5 `composer_v5` · GT V1 `_Tables` freqlo/freqhi
  rebuild) → a Move-1 factor-candidate. Distinct from **C2** (off-table PROGRAM tables;
  this is off-table DATA lookup).
- **TRANSITION reads — deferred note-init / soft notes (2026-07-06, Bladeswede,
  DMC v4):** the reach model must enumerate more than (instrument's offsets ×
  that instrument's row notes). Notes are FETCHED on one play() call (curnote +
  base update) but note-init (wave restart) can be DEFERRED to a later call —
  an intervening wave-step call runs the OLD instrument's program with the NEW
  curnote; and a SOFT ($7C) note skips note-init entirely, so the old program
  runs for the note's whole duration. Off-table idx = old-program offset + new
  note (Bladeswede: noise-arp off 52 + soft note 47 = idx 99 → hi read $170A =
  V1 track-ptr hi, runtime $1B vs file-image $00). Extract fix: track the
  RUNNING instrument per voice during enumeration; for every note row also
  add_note(note, running); soft rows don't update `running`. The existing
  post-init correction then captures init-set state bytes.
- **SUBTUNE-AWARE post-init correction (2026-07-08, Cool_Musax, DMC v4):** the
  off-table byte can be PER-SUBTUNE init-written state (track-ptr slots
  $1707-$170C are set from the tune record at init — constant within a subtune,
  different across subtunes), and the post-init capture sampled only the
  DEFAULT start song (Cool_Musax sub 1: off 60 + note 36 = idx 96 → $1707 =
  V1 track-ptr lo, start-song $F8 vs reading-song $17). Extract fix: the reach
  model records WHICH songs reach each `(inst, off, note)` record
  (`m.offtable_songs`); `_correct_offtable_postinit` samples `_postinit_values`
  per reaching subtune (`--subtune`) and uses a record's reaching-song value
  only when every reaching song was sampled and they AGREE; any ambiguity
  (idle records carry no attribution, disagreement, missing sample) falls back
  to the start-song sample = the old behavior. Regression-safe by construction:
  a FULL member's served value already matched every subtune's stream, so the
  reaching-subtune capture returns the same value → byte-identical build.
- **THE LEAD-IN READ, AND THE THREE WAYS ITS CAPTURE FAILS (2026-08-23, Pride +
  Chronic_Music_3, DMC v5 family-4):** before a voice's first note it idles on
  the wave program at index 0 with the per-voice LEFTOVER note, so the
  reach model must enumerate `(idle step offset × leftover note)` as well as
  the per-instrument pairs. All three ingredients of that capture failed at
  once, and each is a distinct transferable trap:
  1. **ORDERING — a variant's state-ADDRESS correction ran AFTER its
     consumer.** The capture reads `m.lo_notes`; the family-4 block that
     re-points those notes from the canonical `$100F` to the variant's `$1012`
     ran two lines LATER. The capture therefore enumerated decoy bytes, which
     indexed INSIDE the table, so the `idx > 95` test never fired and every
     lead-in off-table read was silently dropped. ⚠ GENERAL RULE: **when a
     variant block re-points a state address, grep for readers of that field
     ABOVE it, not only below** — the correction existing and being correct
     says nothing about it running in time. Nothing detects this: the wrong
     values are well-formed and the build succeeds.
  2. **A "no leftovers" GATE that is not one.** The block was gated on
     `any(lo_notes)`, but note `$00` is an ORDINARY note and it is the idle
     program's own step OFFSETS that push the index off-table (Chronic_Music_3:
     note $00, idle offsets 251/254 → idx 251-254). On the variant the gate had
     been passing for the WRONG REASON (the decoy bytes were usually non-zero),
     so fixing (1) exposed it as a member going SHALLOWER — the C5 depth rule
     catching a defect inside a single round.
  3. **VALUE = the POST-INIT byte, not the file image.** The lead-in read
     happens on the first play(), so init has already run. Where the source
     address is inside the init's clear window the runtime byte is `$00` while
     the file image still holds the packer's leftover (Pride V1 hi: file `$06`,
     runtime `$00`). v5 probes the member's own clear loop statically
     (`_init_clear_range`, C19's method); **v4 already has the general form** —
     `_correct_offtable_postinit`/`_postinit_values`, which MEASURES the bytes
     with `siddump --memwatch` and keeps only those constant across the sample,
     covering init-WRITTEN bytes too, not just init-zeroed ones. The v5 variant
     is deliberately narrow (adopting v4's would change captured values for
     1,132 canon v5 FULLs); **converge on the v4 mechanism, do not grow a third
     variant.** Move-1 factor-candidate alongside the composer reconstruction.
  Gate used, and the right one for this class: build EVERY family member in a
  pre-change worktree and after, MD5-compare, and verify only the changed set —
  167 changed (all family-4, zero canon), deeper 11 / shallower 0 / regressed 0.
- **GT V1 consumer (2026-06-30, commit 8a743d1):** `extract/to_usf._offtable_freq` —
  per-inst reachable reads (wave/arp/**bare-note** idx≥96, via a cross-pattern
  instrument-carry walk; the bare-note read `freq[note]` for note+transpose≥96 was the
  key case the FC/DMC players don't have). Encoded `(idx,0,lo,hi)` (GT's freq table is
  global → idx is the off-table note index). **TWO GT-V1-specific lessons:** (1) the
  composer must PAD its internal freqlo/freqhi to a stable ≥128 size — a per-tune-varying
  array size shifts the BSS, changes page-crossing branch cycles, and drifts the song-end
  capture boundary by a partial frame (a `sig=len` flip, Trap B — NOT a value divergence;
  diffing a pre-migration baseline was what isolated it). (2) The migration here is
  CORRECTNESS-NEUTRAL ML-cleanliness, NOT a convergence fix: GT V1 reads cap at idx≤~110
  (note≤93 + offset), the old 128-window already covered them, so 0 FULL-count change
  (164→164, 0 status changes vs baseline). Verify before assuming an off-table read is
  the divergence cause (the GT V1 deep partials looked like C6 but are wrong-NOTE).
- **MUSIC ASSEMBLER consumer (2026-07-22, 4th):** two read sites, both
  `freqlo[idx]`/`freqhi[idx]` — NOTE `idx=(orderlist transpose+note)&$FF` (≤110)
  and ARP `idx=(step+curnote)&$7F` (≤127, a 7-BIT mask, not C6's usual 8). Uses
  GT V1's global-table `(idx,0,lo,hi)` encoding. THREE things worth carrying
  forward: (1) **the sibling table is not necessarily what you overrun into** —
  MA's `freqhi` sits BELOW `freqlo`, so the hi read lands in the PLAYER'S OWN
  CODE (freqhi+97..99 = `LDY $C3D9,X`) and the orig plays opcodes as
  frequencies; do not assume the C6 lo/hi geometry, read the two base addresses.
  (2) the reach walk must carry the running instrument AND the running note
  ACROSS sequence boundaries — both persist (a preset select is sticky; a rest
  or hold leaves `curnote` alone while the arpeggio keeps stepping), so a
  per-sequence walk under-captures. (3) **off-table reach is a near-perfect
  verdict predictor** and is worth measuring BEFORE building anything: 43 of 48
  sample partials had off-table reads, 11 of 12 FULLs had none — which is what
  justified spending the round on C6 rather than guessing. Sample 12/60 → 41/60
  FULL. Occurrences: [[project_music_assembler_target]].
- **GLIDE-ARRIVAL reach + event-driven record CREATION (2026-07-24, DMC v4
  r116, Gomez/Psycho_One):** a slow glide's ARRIVAL reloads curnote = the
  glide TARGET ($1481 `TYA / STA $1012,x`) — and glsp survives the
  intervening rows, so the arrival can land many frames later, under a
  LATER instrument's still-running wave. The glide-to-note-0 dive idiom
  then sends that wave's negative offsets off-table (idx 255..247) — reads
  NO static row walk can enumerate (the target note never appears on the
  reading instrument's rows; the glide row itself names a different
  instrument). TELL: a V-freq divergence whose memwatch shows curnote=0
  (or = a glide target) with wnote wrapped and an instrument that has no
  note-0 rows; the two writers of curnote are the note-load AND the
  glide-arrival ($1482). FIX: the event-driven capture (which observes
  exact (inst, off, note) keys at the read moment) gains a CREATION path —
  records the static model missed are created for keys whose note is a
  walked GLIDE TARGET and whose offset is one the instrument actually
  steps (snapshot-skew keys fail that test; wavepos idx 211-213 stays with
  the layout machinery). The capture itself is gated on a static risk
  test (glide targets × shipped wave offsets indexing past the table onto
  a nonzero non-redirect byte — 758/5401 f1 members, +1 siddump each at
  extract; 12/12 sampled FULLs create nothing and emit byte-identical
  USF). NB `dmc_offtable_probe` mis-attributed this read by value (its
  6th mis-fire: the diverging $2A coincided with $172A=sectpos) — pc-trace
  the ACTUAL store first, per the C11 warning.
- **Boundary:** reachability = offset values × played notes × transposes
  (conservative over-approx). With exact per-read capture an under-capture diverges
  in verify (never silent). **GOTCHA — the dual lo/hi read:** the off-table read is
  BOTH `freqlo[idx]` and `freqhi[idx]`; with contiguous freqlo[entries],
  freqhi[entries],window the LO read at idx≥2·entries lands DEEPER in the same
  window (pos idx−2·entries) than the HI read (pos idx−entries). The composer must
  populate BOTH positions (provably the same byte, `mem[hi_base+idx] ==
  mem[lo_base+idx+entries]`). A contiguous window hides this; exact capture exposes
  it (FC At_War class, 2026-06-21).
- **Consumers:** FC standard (`engine_model._std_offtable_freq` → 2528 FULL,
  freq_overrun blob eliminated, 2026-06-21); DMC v5 (`engine_model._assign_offtable_freq`
  → 1041 FULL, blob eliminated, 2026-06-21). Both `freq_overrun`-free; the schema
  field removal is the pending cleanup (`deprecated/old_docs/offtable_freq_plan.md` Phase 7).
