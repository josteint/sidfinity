### C34 — a packed-stream byte whose meaning depends on the DECODER'S POSITION

- **The problem class:** an engine's command stream is decoded with a
  per-byte dispatch map (`$00-$5F` note, `$60-$7F` rest, `$80-$9F` select,
  `$A0-$FF` hold, `$FF` terminator). But some COMMAND HANDLERS consume the
  bytes that follow them THEMSELVES, and when they do they apply their own —
  usually coarser — rules instead of re-entering the top-level dispatch. The
  same byte value therefore means different things at different stream
  positions. A decoder written from the dispatch map alone is wrong exactly at
  those positions.

- **Worked example (Music Assembler, 2026-07-22).** The preset-select handler
  ends with `INY / LDA ($FA),Y / CMP #$60 / BCS <rest handler>`, falling
  through to the note handler. So after a preset select:
    * `$A0..$FF` is a **REST** (gate released), not a HOLD — the `$A0`
      sub-split lives only in the command-class handler this path skips;
    * `$FF` is a rest of duration `$1F`, **not end-of-pattern** — the
      terminator test sits at the top of the next iteration and is only
      reached after a COMPLETED event.
  6% of members (77 sites in a 400-member sample) hit it.

- **WHY IT IS DANGEROUS — the project's own verdict cannot see it.** If the
  composer re-emits the stream from decoded events and its player mirrors the
  same handler shape, a mis-decoded byte round-trips to a byte the player
  reinterprets identically. The write stream matches, the member verifies
  FULL, and the defect is invisible to `verify_all` / the family batch /
  regression forever. What it corrupts is the USF CONTENT — here a `tie`
  (hold) minted where the music has a rest — i.e. exactly the training data
  the whole pipeline exists to produce. This is the class of bug the Core
  Tenet's write-stream oracle is structurally blind to, so it must be found by
  READING THE HANDLER, never by waiting for a verdict to fail.

- **Canonical solution:** decode with the position state the player has. Carry
  a one-byte "the previous command consumed me" flag (or a small decoder mode)
  and give each consuming handler its own dispatch, transcribed from the
  handler's actual branches rather than from the format table. Re-emission then
  needs no special case: a post-preset rest re-emitted as `$6x` is dispatched
  by the player exactly like the original's `$Ax`, so the fix is behaviour-
  preserving (MA: Sid_Slam unchanged at 85,574 writes; 3/8 quirk-carrying
  members still FULL, matching the family baseline).

- **TELL / how to look for it:** in the player's disassembly, find every
  handler that does `INY / LDA (ptr),Y` before returning to the dispatch loop.
  Each one is a position-dependent site. Cross-check its compare chain against
  the top-level map — a SHORTER chain (`CMP #$60` where the top level does
  `BMI` + `CMP #$A0` + `CMP #$FF`) is the signature: the handler has collapsed
  several top-level classes into one.

- **Do not confuse with C22** (two engine ops rendering to overlapping USF flag
  sets, which DOES diverge in verify). C34 is upstream of the representation:
  the event stream is already wrong before any USF encoding decision is made,
  and nothing downstream can notice.

- **2nd occurrence — the DMC v4 TRACK layer (Creo/Dance + Experiment,
  2026-07-23, round 100).** The track fetch's TRANSPOSE handler consumes the
  following byte ITSELF (`INY / LDA ($f8),y / TAY`, $10FE-$1101) as a SECTOR
  NUMBER, skipping the top-level `$FE`/`$FF` tests — so a track tail
  `...$A0 $FF` plays ONE ROW of secp[$FF]'s pseudo-sector (the composer
  deliberately aimed the garbage index at a real outro phrase at $1C1C).
  Two engine facts compound it: (1) the track byte is RE-DISPATCHED at
  every row fetch, so the next fetch reads the same position as a track
  byte and loops; (2) the `$FF` loop handler does NOT zero the sector
  position ($1729 is only reset by the sector's own `$7F`), so the
  loop-target sector RESUMES mid-stream at the garbage row's consumed
  byte count — skipping its leading instr/dur command bytes, which then
  INHERIT sticky state (C32). `_walk_track` mirrored the dispatch-map
  reading (post-transpose byte re-dispatched, sectors simulated to their
  own terminator, loop resets position) and decoded an endless junk outro.
  UNLIKE the MA occurrence this one IS write-stream-visible (our composer
  does not mirror the quirk), presenting as a ~95%-in divergence at the
  track wrap where the orig plays real content and the rebuild drones.
  FIX: `_walk_track` consumes the post-transpose `$FE`/`$FF` as a one-row
  pseudo-sector entry, then re-dispatches it as a track byte with the
  consumed byte count carried into the loop target (`pending_off`); the
  to_usf stated-orderlist fold REFUSES intro/loop variant pairs that
  differ in stated content or duration (one physical slot cannot encode
  both passes — legacy unrolled representation carries the member; the
  refusal also cured the Rayden 2SIDs' latent carried-duration collapse).
  Same lesson as the MA case: the handler's real branches, not the format
  table, define the byte's meaning — READ THE HANDLER.

- **3rd occurrence — the SAME quirk must reach EVERY mirror of the walk
  (Flyt/Rock_Tec_Tec +6 more, 2026-07-24, round 112).** The r100 fix taught
  `_walk_track` the post-transpose consumption, but the two C29 GATE walks
  (`_offimage_sectors`, `_undefined_secp_reads`) still skipped every byte
  after a transpose — so a tail `a0 ff` whose pseudo-sector is
  secp[$FF] = $0000 (live zeropage) never triggered the zp overlay, and
  `_walk_track`'s probe then simulated IMAGE ZEROS, got `('endless', …)`
  (garbage has no $7F terminator), and dropped the row: the rebuild droned
  the held note at the wrap while the orig sonifies the 6510 port ($2F =
  note 47). TWO fixes: the gate walks consume the post-transpose byte and
  window-check secp[$FE/$FF]; the probe accepts the 'endless' simulation and
  takes ROW 0 (all the engine ever plays before re-dispatching). LESSON:
  when a decoder quirk is taught to the main walk, grep for every OTHER
  function that "mirrors the track walk" — a gate that under-approximates
  reachability silently disables the downstream machinery that depends on
  it. Census: 16 f1 carriers; 9 FULL unchanged, all 7 partials flipped FULL.
- **4th occurrence — the ONE-ROW LAW GENERALIZED to $80-$FD: the consumed
  byte MUTATES ROLES between invocations (Harti/Memomania sub 3 FULL,
  2026-07-27, round 120).** The engine re-reads `track[pos]` on EVERY
  duration expiry (only $7F advances pos; sectpos persists). So the byte the
  transpose handler consumed as a sector number is re-dispatched BY TRACK
  RULES on the next invocation: `$FF` loop / `$FE` stop (the 1st/3rd-occ
  form) — or, for `$80-$FD`, **ANOTHER TRANSPOSE**. Memomania's KERNAL-ROM
  orderlist `$F3 $A5 $BA $D0 $03`: each garbage byte plays ONE row of its
  sector (secp[$A5]=$0000 port/zp, secp[$BA]=$FFFF 16-bit wrap,
  secp[$D0]=$00FF stack page) then becomes tr +5/+26/+48, landing the REAL
  sector #$03 at tr $30 — and the endless $0000 tail then plays note 0+48 =
  the dominant held note. Proven by the live pc-watch sector-ptr run-length
  + the otrk/transp memwatch stepping tr 53→05→1A→30. THREE mechanics the
  one-row path needed: (a) cover `b >= $80` (not just `>= $FE`); (b) the
  row's consumed bytes ACCUMULATE in the persistent sector position
  (`pending_off` += consumed; the next sector — even a full one — starts
  there); (c) the post-row sub_11E6 `$7F` PEEK can advance the track
  immediately (the byte then never re-dispatches). The accumulated sectpos
  is OBSERVABLE (off-table hi reads at idx 130-132 = $1729-$172B), so the
  composer's sectpos shadow gained per-entry BASE THREADING driven by a new
  stated byte-fact row flag `runon` ("no $7F follows — sectpos not reset"),
  emitted only on one-row garbage rows; every member without the flag is
  byte-identical (base stays 0, last-row-0 rule intact).
- **5th occurrence — THE MIRROR IMAGE: the decoder REFUSES what the player
  ACCEPTS (DMC v5, 2026-08-25).** The four prior occurrences are all "our walk
  assigns a byte the wrong MEANING". This one is the same root discipline
  (mirror the dispatch, read the handler) failing in the opposite direction —
  the walk manufactures an ERROR where the player has perfectly defined
  behaviour. It took out 14 members as batch `error` rows, the entire v5 error
  bucket. Three facts, all sitting in `pipelines/dmc/v5/disassembly.s`:
    * **An unrecognised `>=$80` sector byte is a 1-BYTE NO-OP.** The dispatch's
      CMP chain ends `$12A2 CMP #$F6 / BNE $1289`, and `$1289` is
      `INC $17d8,x / JMP $1158` — the fall-through re-uses the $F1 handler's
      second INC as a 1-byte skip. It emits no write and consumes no duration,
      so DROPPING such bytes from the event list is lossless and re-emission
      needs no special case. `_decode_sector` raised `unknown sector cmd`
      instead (7 members).
    * **THE POSITIONS ARE BYTES** (`$1158 LDY $17d8,x` sector, `$10FC LDY
      $17d5,x` track), so both wrap mod 256. A stream with no `$FF` inside its
      256-byte window CYCLES; walking `pos` linearly past 256 reads bytes the
      player can NEVER reach — inventing phantom terminators beyond offset 255
      (Praiser/Sid_Extension's real `$FF` sits at offset 278), and running off
      the end of memory (`IndexError`) on a file's last sector. This half is
      C11's 8-bit-index rule applied to the STREAM POSITION rather than to a
      table index, and C2's "bound by reachability, not nominal length".
    * **A SIZE INFERRED FROM AN ADDRESS DELTA IS NOT A COUNT** (C39's shape):
      `n_sectors = secp_hi - secp_lo` assumes the two pointer tables are
      adjacent, but they are reached through independently-relocated operands —
      four bytes apart in the reference player — and the engine indexes both
      with an unchecked byte. Used as a bound the delta both overstates and
      understates (an orderlist referencing sector 32 against a 26-entry delta;
      two members whose delta is NEGATIVE). Bound by what the tracks reach.
  ⚠ Correcting the decoder to stop raising SILENTLY DISABLED TWO GUARDS that
  were written as `except RuntimeError:` around it, one of which took a FULL
  member down — the discipline and its recipe live in
  [[feedback_relaxing_an_error_kills_its_guards]], for which this is the worked
  instance. The C34-specific residue worth keeping here: what a decode-guard is
  really testing is almost always "the stream never states an end", so the
  corrected walk must emit that as a POSITIVE tag (here `wrap`, which `to_usf`
  reads as an ordinary loop) instead of leaving it as an exception.
  ⚠ **A TERMINATOR MAY ONLY COUNT IN ONE POSITION — check WHERE it is tested.**
  The same session's second half: `$FF` ends a DMC v5 sector, but ONLY as the
  lookahead `step_commit` peeks immediately after committing a ROW ($118C, and
  note_on's own copy at $1314). The dispatch CMP chain has no `$FF` case at all,
  so an `$FF` the dispatch READS is just another unlisted byte and takes the
  1-byte no-op above. A sector ending `... note, $FD nn, $FF` therefore does NOT
  end — the command runs, the `$FF` is skipped, and the voice RUNS ON into the
  following bytes. Treating `$FF` as end wherever it appeared made those sectors
  look like terminated sectors with orphan trailing commands, which is what the
  `trailing_sector_cmds` refusal was actually seeing. Two of the three members
  went straight to FULL once the walk matched the player — an exact write-stream
  match being the empirical proof of the reading. GENERAL: for any stream
  terminator, find the instruction that TESTS it and note what must precede it;
  a terminator tested only in one position is a different language from one
  tested at every dispatch. (This also refuted a planned fix: the "are the
  trailing commands dead?" question was unanswerable-as-posed, because there is
  no next sector for the state to survive into.)
  Exposure measured before landing (decode-only sweep, all 2,031 v5 members):
  26 members change, of which exactly 1 is FULL and provably unreachable
  (verified still FULL). Result: 11 members build, 2 refuse cleanly under a new
  named `data_tables_off_image` reason (C26-shaped, 9/12 operands outside the
  image), 1 joins the pre-existing `filter_table_overflow` bucket; 3 reach FULL.
