### C37 — subtune SAVE-STATE RESUME wrapper (per-subtune state copy + data pokes; only init-wipe SURVIVORS matter)

**Problem class.** A member's PSID header claims N subtunes but the player's
tune table has ONE real record; the init vector points at an APPENDED wrapper
that (1) copies a per-subtune ~65-byte ENGINE-STATE SNAPSHOT into the player
via an SMC copy loop (X = subtune selects the source page; a dest-address
pair table names scattered state bytes AND song-data bytes), then (2) forces
`LDA #0` and jumps to the real init — every "subtune" is the SAME song,
differentiated only by the pre-loaded state. The author's snapshot is a raw
save-state dump: most of it lands inside the player's init wipe and is DEAD
CARGO.

**How it presents.** One subtune FULL, the other(s) diverging at play
position 0 with `state_match=False` — the first fetched row plays a
DIFFERENT note/instrument than the walk decoded (the orig plays the copied
sticky curnote/instrument cache; the extract walked the file-image data).
The extract's decode is not wrong about the bytes — it is reading the
PRE-COPY image for a subtune whose memory was patched before init.
`--memwatch-on-write D406 <curnote/cache/trkptr slots>` at the first
note-init shows both subtunes loading the SAME tune-record pointers (the
giveaway that the header's subtune count is not the player's).

**Canonical solution (shape; first carrier not yet landed).**
1. DETECT by observation, never by parsing the wrapper (C18/C31 rule): run
   the FILE's init(A=sub) under py65 per subtune and diff POST-INIT memory
   against the start-song's post-init memory. py65 is trustworthy here —
   every surviving byte is file-loaded or init-written (no deep playback,
   [[feedback_ground_truth]] third-mode caveat does not apply).
2. Keep ONLY the init-wipe SURVIVORS (the copy runs BEFORE init): bytes
   below/above the wipe range. Everything the wipe covers is dead cargo —
   do NOT try to represent it.
3. Survivors split by the trichotomy: sticky curnote / instrument-cache
   bytes → the EXISTING per-subtune `init.voice_state` priming fields
   (§4.5; note/instr — no schema addition); SONG-DATA pokes (sector/track
   bytes) → per-subtune WALK MEMORY: extract each subtune's songs from that
   subtune's own post-init memory view, so the poked track/sector bytes
   flow into per-subtune orderlists/patterns naturally (pattern dedup keeps
   them apart). Any surviving byte inside the PLAYER body (custom var /
   SMC operand) must be identified from the member's disasm before landing.
4. The verify's per-subtune verdict needs no change — each subtune builds
   from its own decoded content.

**Boundary.** Distinct from C31 (compilation: N INDEPENDENT players — here
there is one player, one song, N entry states) and from C19 data pokes (a
static wedge poking ONE value — here the poke set is per-subtune and
selected at init). The wrapper's wiped-state bytes must NOT be lifted into
USF (they are unobservable mechanism).

**Landed machinery (2026-07-28):** `factory._state_resume_probe` (static
anchored skeleton decode of the copy loop — SMC wiring verified
instruction-by-instruction, source lo-byte INC wraps within its page per
C11) → `cfg.forced_subtune` + `cfg.subtune_state_copy` ({subtune: {addr:
survivor byte}}); the extract applies the survivors to that subtune's
WALK memory (the same per-song `smem` overlay as glide_neutered — the
sticky-instrument seed read comes per-subtune for free) and lifts the
copied curnote/gate-mask bytes into the existing `DmcSong.idle_notes/
idle_masks` per-subtune priming. Both carriers' non-start subtune now
decodes the CORRECT song (was a garbage record walk).

**Second layer, RESOLVED (2026-07-28, same day) — the copy also edits
FILE-LEVEL tables, carried by C31 CLONE-AND-REMAP, no schema.** The
surviving pokes can land in the WAVEFREQ table (Calf_Love_2: positions
12/15/17 — the two subtunes hear different arpeggio offsets at the same
program step) and the FILTER DEFS. The honest carriage is the C31
clone-per-value-class: re-decode each poked subtune's used instruments
(+ referenced filter defs) under that subtune's patched tables; where
content differs, clone the instrument (and its filter def) and remap
that subtune's rows. Two audibly different programs = two instrument
points, honest content.
- ⚠ A per-subtune `wave_table` cell-override SCHEMA was drafted first,
  on the belief the cells were POSITION-LOCKED (wavepos-carrier
  members). That classification was an ARTIFACT of the pre-C37 garbage
  record walk — with the correct decode the members make NO wavepos
  reads, no position is observable, clone-and-remap suffices, and the
  schema was REVERTED per name-on-proof (the discipline working as
  designed: the alternative-exhaustion step killed the addition). The
  per-subtune stated-cell override remains the recorded shape ONLY for
  a future carrier whose poked positions ARE observed.
- ⚠ C11 inside the fix: a clone filter def must land in an UNUSED
  NIBBLE slot (0-15) — the engine's def index is a record nibble and
  the composer's step base is slot*16 in 8-bit arithmetic, so slot 17
  silently wrapped onto slot 1's zero deltas and froze the sweep.
  Repurposing an unused slot is safe only while no referenced def
  walks off-record (repeat > 5, the C2 window); otherwise skip.

**Detection is now OBSERVATION-FIRST (2026-07-30, 3rd carrier).** The 2nd
wrapper SHAPE (PVCF/Cafe_Odd: `JMP copy` form, single src-lo table + dest
lo/hi tables, `LDA #$00` before `JMP base`) proved the C18/C31 rule this
entry already stated: don't teach the static parser new shapes.
`factory._state_resume_observe` (fallback when the static skeleton
misses): run the FILE's init(A=sub) under py65 per header subtune,
record A at the FIRST entry into base; fire iff every subtune enters
with the SAME A AND ≥1 non-start subtune's post-init RAM differs from
the start subtune's (≤256 bytes — more suggests a C26 unpacker, refuse).
The post-init diff IS the survivor filter (wiped bytes cancel). LIMIT:
survivors are relative to the START subtune — a start-subtune poke
differing from the image is invisible (would present as sub-0 partial).
New survivor CATEGORIES lifted by the extract (beside idle_notes/instr
seeds + walk-memory + wave-cell clones): the d417 routing SHADOW poke →
per-song `d417_shadow` → subtune `init.sid.filter.res_routing`; the
GLOBAL slide/vibrato half-rate parity poke ($1019 twin) → per-song
`dual_phase` → subtune `init.slide_phase` (both fields pre-existed —
zero schema additions). Cafe_Odd's V3 wave-phase divergence 21 s in was
the parity seed: vibrato-flagged instruments alternate wave-step vs
vibrato on that ONE global counter, so a resumed phase shifts every
such voice's wave program by one play.

**Status:** recurring (3×), all carriers FULL — Rio/Calf_Love_2_everytime
(wrapper $20C2, sources $2173/$21B4) + Rio/Calf_Love_everytime (wrapper

## 4th occurrence — FIRST NON-DMC CARRIER, and the degenerate form

**(2026-08-09, Hubbard '85 / Human_Race, HVSC #85.)** The class is not
DMC-specific. HVSC #85 re-rips Rob Hubbard's Human_Race with a 6th subtune,
and it arrives in exactly this shape: the PSID header declares 6 songs while
the engine's own song table still holds 5, and an APPENDED init wrapper does
the rest —

    B1A3  LDX #$00 / STX $D417 / STX $D412 / INX      ; X = 1
          CMP #$05 / BCC +3 / LDA #$04 / INX          ; sub 5 -> song 4, X = 2
          STX $A454 / JMP $A000                       ; poke, then the real init

This is the DEGENERATE case of the entry above: one data poke, no state
snapshot, no survivor analysis. $A454 is song 4's entry in the per-song TICK
table $A450-$A454, so subtune 6 is song 5 replayed one tick slower — the
changelog's "as slow as Rob Hubbard wanted in 1985". Worth recording because
it shows the minimum viable form: **a wrapper that pokes a single table byte
is the same problem as one that pastes a whole state block**, and a static read
of the file image is wrong for both — the byte at $A454 is $01 on disk and $02
for the subtune that plays it.

Landed as an observed map (`SUBTUNE_SONG` / `SUBTUNE_TICK` in the engine
config) plus two optional extract args (`song_index` / `speed_override`),
defaulting to identity so every other Hubbard rip is byte-identical by
construction. All 6 subtunes verify.

**REFINEMENT — measure with siddump, not py65.** This entry's canonical says
"py65-diff post-init memory". That is right when the survivor only steers
extraction, but here the poked byte is a TEMPO: it reaches the write stream,
which puts it under [[feedback_ground_truth]]'s third failure mode. Use the
native captures instead — `--pc-watch <real-init PC> 0-2 --pc-watch-first`
gives A (the song) and X (the poked value) at the moment control transfers,
and `--memwatch <table>` gives the table as the engine will read it. py65
happened to agree here; that is not a licence to skip the check.

⚠ **`--peek-post-init` CANNOT read a player in the $A000-$BFFF range.** This
player loads at $A000, and the peek snapshots the IDLE-time 6510 port ($37),
where BASIC ROM is banked over exactly that window — it returns ROM bytes
(`AA 20 45 AB A0`), identical for every subtune, which reads as a plausible
"nothing changes per subtune". Ledger C29 already states this ("peek-post-init
LIES there ... memwatch is truth"); it is restated here because C29 frames it
as a stray off-image read, and this is the ordinary case of a player that
simply lives high in memory.

**Status:** recurring (4×), all carriers FULL. First non-DMC carrier, which
makes the class cross-family and therefore Move-1 relevant: the
"observed subtune -> (song, knob) map" wants ONE representation, not a
per-family one. Occurrence detail: `pipelines/hubbard/human_race/config.py`.
