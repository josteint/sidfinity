### C13 — Engine-variant dispatch: shifted init, canonical play body
- **The bug class:** a player family has sub-variants that differ ONLY in the
  init/dispatch header while the per-frame PLAY body — the code that emits the
  `$D4xx` write stream — sits at the SAME relative offset as the canonical
  member. A dispatch keyed on the init handler's offset (or a full-image code
  compare) rejects these variants (`no_jumptable` / `player_code_mismatch`),
  even though their play body is byte-identical and every operand site is in the
  unshifted body. Because the composer EMITS ITS OWN init (universal reset +
  typed priming, never reproducing the original's init writes — see the CORE
  TENET and the init-trichotomy), the init handler's layout is IRRELEVANT to the
  write-stream verdict; only the play body matters.
- **TELL / how it presents:** a cluster of build-fails whose jump table has the
  canonical PLAY target (e.g. DMC family-2 `JMP base+$85`) but an init target a
  few bytes off (`base+$38..$3A` vs the canonical `base+$37`). The play body
  decodes cleanly; only the init region differs.
- **Canonical fix:** dispatch on the PLAY-body signature, NOT the init offset.
  Accept the variant, extract operands from the (unshifted) canonical play-body
  sites, emit your own init, and let BUILD+VERIFY (the write stream) be the
  judge. A loosened dispatch can never false-FULL — a genuinely-different engine
  that happens to share the play offset extracts garbage operands and verifies
  partial, not full. Keep the init-offset window tight enough to be principled
  (near the family's real init region) but don't gate on an exact match.
- **Status:** logged (DMC family-2 `_jt_layout` play+$85 / init∈[+$30,+$40],
  commit 2a07a7e; +12 FULL / 2 correctly-partial / 0 false-accept). Composes with
  the earlier build+verify-gate change (aaa914c) that replaced the family-2
  code-identity hard-reject with a `break` + build+verify judge — same principle
  (the write stream judges, not code identity), one round apart.
- **Consumers:** `pipelines/dmc/v4/factory.py` `_jt_layout`. WATCH-LIST: any
  feature-driven family whose detection compares init/dispatch code — the
  verdict is the play stream, so dispatch should key on the play body.

## DMC V5 — a THREE-entry jump table on a canon play body (2026-08-23)

The canon family-3/5 V5 player has a TWO-entry jump table (init, play). The
C18 wrapper members carry a THIRD entry at `base+6` pointing at an appended
effects-only routine (canon `run_effects` per voice behind a per-voice gate
table), while `base+3` still points at the untouched canon play body and the
init is re-implemented elsewhere.

So the entry-count is NOT a family discriminator, and dispatching on it would
reject a member whose play body is perfectly canonical — the same failure the
card's main rule prevents for a shifted init offset. Dispatch on the PLAY-BODY
signature; treat extra jump-table entries as a variant's own extension, and a
useful OBSERVATION HANDLE (watching `base+6` is what makes the C18 schedule
readable — see C18's 2026-08-23 section).

## DMC V5 — a jump-table HEAD SHAPE is not a player identity (2026-08-27)

The card's main rule says dispatch on the PLAY BODY. Its dual is the failure
this section records: a dispatch that keys on the jump table's OFFSETS and then
checks *nothing else*.

V5's family-4 branch admitted a member on `JMP base+$40 / JMP base+$95` alone —
no body compare at all, unlike the family-3/5 branch's masked reachable-
instruction compare — and then applied a FIXED operand-site map
(`FAMILY4_SITES`) to read the song's data-table addresses. One HVSC member
(`MUSICIANS/E/Ed/We_Were_All_Kids`, hand-built by the author) wears that head
over a completely different program: 2.0% byte-identical to the family-4
reference over the code window, where the other 649 carriers run 47-100%. The
site map landed mid-instruction, so the "orderlist address" was a `STA`
opcode byte ($9D) plus its operand low byte ($D8) read as `$D89D`, and the
member surfaced as a nonsense `data_tables_off_image` refusal naming an
address that was never an address.

**Validate what you are about to CONSUME, and detect the minority
POSITIVELY.** Two separate questions, and conflating them is what makes a fix
regress:

- *Consumption precondition* — at each operand site, is the instruction the
  one the site map says is there? Cheap (12 byte compares), exact, no
  reference blob, and it directly guards the only thing the map is used for.
- *Player identity* — do NOT reach for a full-body compare here. Measured over
  all 650 family-4-head members: 628 have ZERO opcode mismatches across the
  700 play-reachable instructions, but the wedged/re-assembled ones run to
  202 and 286 mismatches — and every one of those is a currently-BUILDING
  partial. A strict body compare would have refused 22 members in the residue
  queue. A percentage threshold splits the same population arbitrarily.

The non-arbitrary discriminator falls out of the consumption check: **ALL
TWELVE sites wrong.** 647 members match 12/12, the two most re-assembled ones
10/12 and 11/12 (a wedge at their filter sites), the impostor 0/12. "Not one
site is where it should be" is the literal statement of "these offsets do not
describe this program" — no threshold is tuned, and nothing that builds today
is refused. Jupiter41 stays the DEFAULT; the alternate player is detected
positively by a structural signature of its init with every packer-patched and
relocated operand byte wildcarded (one carrier in HVSC under a family-4 head;
14 other files carry the same skeleton at other offsets under other heads).

**A head shape can hide a DIFFERENT LINEAGE, not just a different build.** Ed's
player turned out to run family-3/5 SEMANTICS (canon track commands
$FF/$FE/$FD/$FC, canon sector commands $F3/$F4/$F5/$F9/$FA/$FD/$FE, canon
8-byte instrument records, canon interleaved tune record, curnote at the canon
base+$0F) at family-4 CODE OFFSETS — so the right answer was its own site map
plus the canon mechanism knobs, not a refusal and not the family-4 knobs. Read
the dispatch chain before assuming which family a variant belongs to; the
entry-point offsets are the least informative thing about it.

⚠ The same audit is owed to every OTHER offset-only dispatch. The scan that
found Ed's player also turned up 11 `MUSICIANS/K/Kosa/*` members sharing one
DMC-derived player at `init +$60 / play +$D1`, routed to no pipeline at all.
