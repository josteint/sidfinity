Before reverse-engineering ANY engine effect (orig instruction sequence,
gating conditions, freq table layout, fx flag bits), check the three
existing research sources **in the order they were acquired** — that
order is the order to read them, family-foundation first:

1. **`pipelines/<family>/docs/`** — engine-family-wide research: format
   specs, player manuals (e.g. `wiki_fc_v41_manual.md`,
   `csdb_fc_v4_player_disasm.md`), CSDB release notes, lineage. This
   is the FIRST thing acquired when work begins on a new player family
   (via the `research-player` skill at `.claude/skills/research-player/`).
   ~47 family-doc dirs exist today (`pipelines/future_composer/docs/`,
   `pipelines/goattracker/docs/`, `pipelines/cheesecutter/docs/`, ...).
   These tell you the player's instruction semantics, instrument
   format, effect catalogue, byte encodings — the foundation
   everything else builds on. Without it, you're re-deriving the
   format from raw bytes.

2. **`pipelines/<family>/<engine>/disassembly.s`** — annotated full
   disassembly per migrated SID (typically generated by
   `tools/seed_disassembly.py` then hand-labelled with routine names
   like `L_7DCA`, `sub_7DBD`). The structural labels alone (which
   addresses are entry points, which are paired writers, what each
   fx bit does) are worth hours.

3. **`pipelines/<family>/<engine>/RE_NOTES.md`** — hand-written RE
   notes per migrated SID covering state-byte assignments
   (`$90DA = wavecount`, `$90F6 = counter2`, etc.), per-frame flow,
   fx-bit decompositions, prior session's findings, known
   partial-cause analysis. Read FIRST, not after a session of guessing.

**Why:** Hawkeye sub 6 investigation (2026-06-06) — I spent a multi-hour
session reading raw py65 disasm fragments of `$8232-$8240`, then
`$812E-$813A`, then `$82A0` CMP — each time forming a wrong hypothesis
because I didn't know what those addresses MEANT. The hand-annotated
`disassembly.s` had structural labels like `L_7DCA` (sustain) and
`L_7E0F` (per-frame inst chain entry); `RE_NOTES.md` had
`$90DA = wavecount` (which would have told me that
`memwatch $90DA = $15` meant V1 was on wave-program step 21, not
inst 21 — different concept). The actual sub 6 root cause was
identifiable in ~5 minutes after consulting these files.

**How to apply:** When you sit down to debug a writelog divergence in
an engine (especially FC family), the FIRST commands of the session
should be:

```bash
ls pipelines/<family>/docs/             # FIRST — family-wide foundation
ls pipelines/<family>/<engine>/         # disassembly.s + RE_NOTES.md
wc -l pipelines/<family>/docs/*.md \
      pipelines/<family>/<engine>/disassembly.s \
      pipelines/<family>/<engine>/RE_NOTES.md 2>/dev/null
```

Read in that order: family docs first (foundation), then per-SID disasm
(structural map), then per-SID RE notes (specific findings). Even
partial material is hugely better than starting from raw bytes.

This is the FC-family analog of [[feedback_full_decompile_hubbard]] —
the Hubbard rule said "do the disasm FIRST"; this rule says "if someone
already did the disasm, READ IT first."
