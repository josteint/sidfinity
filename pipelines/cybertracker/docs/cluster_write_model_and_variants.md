## 1. Overview

**CyberTracker** is a C64 SID music tracker authored by Bjarke Nørgaard Laustsen
(CyberBrain) of No Name, released 2001.

- V1.00: released 2001-04-13 at Mekka Symposium
- V1.01: released 2001-09-14 (current version, adds skins / config maker / file
  compression; 100% file-compatible with V1.00 loading V1.01 files fails ~99.7% of
  the time due to format extension)
- CyberTracker Executable Maker v1.00: released 2001-12-13
- CyberTracker Executable Maker v1.01: released 2001-12-26
- CyberTracker Packer BETA #1: released 2002-03-25 (PC/DOS tool)

HVSC #84 corpus: **255 SIDs** across two sidid engine classifications:
- `CyberTracker`: 125 SIDs
- `CyberTracker_exe`: 130 SIDs

Engine author documentation: https://noname.c64.org/tracker/

## 2. The Two Variants

### 2.1 Sidid signatures

From `sidid.cfg` (cadaver/sidid):

```
CyberTracker
1E BC 46 10 BD B7 10 99 06 D4 A9 00 9D B4 10 99 END

CyberTracker_exe
60 4C F8 49 ?? ?? ?? ?? ?? ?? ?? ?? ?? 4C 84 4A 4C ED 4B END
```

**CyberTracker signature decoded:**
```
1E BC 46 10   ASL $1046,X       (voice Y-base table shift)
BD B7 10      LDA $10B7,X       (load SR cache for voice X)
99 06 D4      STA $D406,Y       (write SR: $D406/$D40D/$D414 via Y=0/7/14)
A9 00         LDA #$00          (zero)
9D B4 10      STA $10B4,X       (clear AD cache)
99 ...        STA $D405,Y       (write AD=$00 -> hard-restart)
```
This is the **hard-restart inner loop** in the `CyberTracker` variant.

**CyberTracker_exe signature decoded:**
```
60            RTS
4C F8 49      JMP $49F8         (dispatch #0)
...
4C 84 4A      JMP $4A84         (dispatch #4)
4C ED 4B      JMP $4BED         (dispatch #5)
```
This is the **envelope program dispatch table** at $47F5 in the _exe variant.
The 13-entry JMP table dispatches into envelope program handlers ($49F8, $4A59,
$4A6B, $4A7D, $4A84, $4BED, and 7 more covering optional/extended programs).

### 2.2 Addressing

**CyberTracker (_ct) addressing:**

| Field | Value | Notes |
|-------|-------|-------|
| PSID load_addr | $0000 (embedded) | actual load always $1000 |
| PSID init_addr | $1000 (35 SIDs) or $1DC0–$2BBE (90 SIDs) | init points directly into engine |
| PSID play_addr | init_addr + $51 (typical) | play = init + offset into engine |
| Engine base | variable: sits AFTER song data | init_addr = engine base |

Why init varies: the _ct format embeds both song data AND engine in one blob starting
at $1000. The first 6 bytes ($1000–$1005) are always two JMP instructions that point
into the engine. Song data fills $1006 onwards (variable length), and the engine
code follows immediately after. As song data grows, the engine shifts upward, so
init_addr rises accordingly.

The 35 SIDs with init=$1000 are simply songs with minimal data (engine starts very
close to $1000).

**CyberTracker_exe (_exe) addressing:**

| Field | Value | Notes |
|-------|-------|-------|
| PSID load_addr | $0000 (embedded) | actual load $0800–$5BA2 |
| PSID init_addr | $53A2 (128 SIDs), $482A (1), $5BA2 (1) | |
| PSID play_addr | init_addr + $40 (always) | |
| Engine base | fixed: $0800 (bootstrap) + engine at $4800–$5600 | |

The _exe format is a **fixed-layout standalone executable** generated by the
CyberTracker Executable Maker tool. It loads at $0800, the engine occupies
$0800–$5600 approximately, song data follows at $5600+, and the init/play
entry points are patched at packaging time to point into the fixed engine.
The 128 SIDs with init=$53A2 are the standard Executable Maker v1.01 layout.

### 2.3 Are they the same engine?

**No.** The _ct and _exe variants share the same musical abstraction (8
graphical envelopes, same voice architecture, same instrument model) and
their $D4xx register write sequences cover the same 25 registers in nearly
the same order. However:

1. **State storage differs**: _ct stores runtime state at absolute $10xx page
   (voice registers at $1090–$10BB); _exe stores state in CPU zero page
   ($49–$80).

2. **Register write ordering differs** for freq lo/hi and PW lo/hi (see §4).

3. **Gate/hard-restart mechanism differs**: _ct uses Y-indexed `STA $D4xx,Y`
   (Y=0/7/14 voice offset); _exe uses self-modifying code (SMC) patching
   inline `STA $D4xx` address bytes at $5554/$555B/$5560.

4. **Code size and structure differ**: _ct engine is ~$1200 bytes embedded
   per-tune; _exe engine is ~$3800 bytes at fixed addresses.

5. **Envelope dispatch**: _ct uses direct subroutine calls; _exe uses a 13-entry
   JMP dispatch table at $47F6.

**Origin**: the _exe is produced by the CyberTracker Executable Maker, which
packages a CyberTracker module into a standalone C64 executable with its own
(larger, fuller-featured) runtime player code. The _ct is the native SID file
produced when CyberTracker saves or exports to $1000 PSID format. Both play
the same musical data, but are different player implementations.

**Migration treatment**: treat as ONE engine family with two distinct runtime
implementations — same USF musical data model but different SID write streams
(due to the freq/PW ordering difference). A single extract path can serve both
if the write-order difference is treated as a config flag.

## 3. Memory Layout — CyberTracker (_ct)

```
$0FFE–$0FFF  (optional 2 bytes):
    69 NN = ADC #NN  — subtune index shift for multi-song files
    (present when init_addr < $1000; the two preceding bytes shift A before JMP)

$1000: 4C XX YY   JMP <engine_init>   (3 bytes)
$1003: 4C XX YY   JMP <engine_play>   (3 bytes)

$1006–$1008: 60 60 60  — padding/marker bytes (three $60 = RTS)
$1009–$100A: 63 74     — 'ct' format magic signature
$100B–$100C: B1 00     — format version ($B1=177, minor $00)
$100D:       NN        — unknown flag (01 for single-tune, 06 observed for 2-tune)
$100E–$101B: 00×14     — zero padding (header zeroed area)
$101C–$102B: PETSCII   — song title (16 bytes, padded with $20=space)
$102C–$103B: ...       — unknown (observed as spaces in samples)
$103C–$1041: 01 02 04 FE FD FB — gate/ctrl mask constants
$1042–$1045: 00 07 0E 00 — voice Y-base table (V1=0, V2=7, V3=14, pad)

Runtime state (zeroed at init; filled during playback):
$1046–$1048: voice Y-base lookup (also 00 07 0E, confirmed by LDY $1046,X)
$1049:       current subtune index
$104A–$104C: per-voice track pointer LO (V1/V2/V3)
$104D–$104F: per-voice track pointer HI
$1050–$1052: per-voice current pattern pointer LO
$1053–$1055: per-voice current pattern pointer HI
$1056:       speed counter init value (set to 6 at init)
$1057:       speed flag (set to 1 at init)
$1058–$106F: various voice state bytes
$1068–$106A: voice active/gate-kill flag (V1/V2/V3)
$106B–$106D: (voice state)
$1072–$1074: (voice state)
$1075–$1077: (voice state)
$1090:       V1 freq lo cache   -> $D400
$1091:       V2 freq lo cache   -> $D407
$1092:       V3 freq lo cache   -> $D40E
$1093:       V1 freq hi cache   -> $D401
$1094:       V2 freq hi cache   -> $D408
$1095:       V3 freq hi cache   -> $D40F
$1096:       V1 pw lo cache     -> $D402
$1097:       V2 pw lo cache     -> $D409
$1098:       V3 pw lo cache     -> $D410
$1099:       V1 pw hi cache     -> $D403
$109A:       V2 pw hi cache     -> $D40A
$109B:       V3 pw hi cache     -> $D411
$109C–$109E: (voice state)
$109F–$10A1: (voice state)
$10A8:       filter lo cache    -> $D415
$10A9:       filter hi cache    -> $D416
$10AA–$10AB: (global state)
$10B0–$10B3: V1/V2/V3 ctrl cache (per-voice X=2,1,0)
$10AE–$10B0: gate-kill flags (per-voice)
$10B4–$10B6: V1/V2/V3 AD cache
$10B7–$10B9: V1/V2/V3 SR cache
$10BA:       filter ctrl cache  -> $D417
$10BB:       volume cache       -> $D418 (init to $0F)
$10CE–$10D0: (voice state)
$10D1–$10D3: (voice state)
$10D8–...:   frequency/envelope tables (song-specific; varies between tunes)

Song data (variable, starts ~$1100 or higher):
    - Subtune track pointer table at approx $1342 (from JSR $3542 in engine):
        [V1_lo, V1_hi, V2_lo, V2_hi, V3_lo, V3_hi] × N_subtunes
    - Per-voice track lists: each = array of 16-bit LE pattern pointers, $0000 terminated
    - Pattern data: pointed to by track entries, per-voice (separate V1/V2/V3 patterns)
    - Instrument/envelope data

Engine code (starts at init_addr = end_of_song_data):
    engine_init  = init_addr
    engine_play  = init_addr + $51 (typical; exact offset from the JMP at $1003)
```

### Track format

Each voice has an independent track (ordered list of pattern references):
```
track_V1[0] = 16-bit LE ptr to pattern for V1 line 0
track_V1[1] = 16-bit LE ptr to pattern for V1 line 1
...
track_V1[N] = $0000  (terminator / restart)
```
The engine reads track entries via SMC-patched `LDA` instructions (patchable
at runtime). Track position advances one 2-byte slot per pattern completion.

### Pattern format (preliminary)

Per-voice pattern data is a byte stream; each line appears to be at least 2–4 bytes
(note byte, instrument byte, effect byte(s)). Exact encoding not fully decoded from
binary inspection alone — see manual for the note/instrument/effect encoding.

## 4. Per-Frame SID Write Model

### 4.1 Pre-write: voice scan (hard-restart)

Both variants first scan all 3 voices (X=2,1,0) for pending hard-restarts:

```
; _ct variant (Y-indexed STA):
LDX #$02
loop:
  LDA $10AE,X         ; gate-kill flag for voice X
  BEQ skip            ; 0 = nothing pending
  STA $10AE,X         ; clear flag
  LDA $10B1,X         ; ctrl cache for voice X
  AND #$01            ; test gate bit
  BEQ skip            ; already gate-off, skip hard-restart
  LDY $1046,X         ; voice Y-base (0, 7, 14 for V1/V2/V3)
  LDA $10B7,X         ; SR cache
  STA $D406,Y         ; write SR (-> $D406/$D40D/$D414)
  LDA #$00
  STA $10B4,X         ; zero AD cache
  STA $D405,Y         ; write AD=0 (instant release)
  LDA $10B1,X
  AND #$FE            ; clear gate bit
  STA $D404,Y         ; write ctrl with gate=0
  ORA #$01            ; set gate bit
  STA $D404,Y         ; write ctrl with gate=1 -> hard restart pulse
skip:
  DEX
  BPL loop
```

```
; _exe variant (SMC-patched absolute STA):
; Table at $552E: {$04, $0B, $12} = ctrl reg offsets for V1/V2/V3
LDX #$02
LDY #$01
loop:
  LDA $5E,X           ; gate-kill flag (ZP)
  BEQ skip
  STA $5E,X           ; clear
  LDA $4F,X AND #$01  ; test gate
  BEQ skip
  LDA $552E,X         ; ctrl reg offset ($04/$0B/$12)
  STA $5554           ; patch: STA $D405,Y target
  STA $555B           ; patch: STA $D4xx (ctrl clear)
  STA $5560           ; patch: STA $D4xx (ctrl set)
  LDA #$00
  STA $49,X           ; zero AD cache (ZP)
  STA $D4FF,Y         ; (patched to STA $D405 = AD=0)
  LDA $4F,X AND #$FE  ; gate clear
  STA $D4FF           ; (patched to STA $D404/$D40B/$D412)
  ORA #$01
  STA $D4FF           ; (patched) gate set -> hard restart
skip:
  DEX
  BPL loop
```

Both implement: **write SR from cache → write AD=0 → write ctrl-gate-clear → write ctrl-gate-set**.

### 4.2 Main register write block

After the hard-restart scan, all 25 SID registers are written from cache in
one contiguous block. The two variants have **identical coverage** (all 25
registers, once each per frame) but **different ordering** for freq and PW:

|---|---|---|
| 1 | D400 V1 freq_lo | D400 V1 freq_lo |
| 2 | **D401 V1 freq_hi** | **D407 V2 freq_lo** |
| 3 | **D407 V2 freq_lo** | **D40E V3 freq_lo** |
| 4 | **D408 V2 freq_hi** | **D401 V1 freq_hi** |
| 5 | **D40E V3 freq_lo** | **D408 V2 freq_hi** |
| 6 | D40F V3 freq_hi | D40F V3 freq_hi |

### 4.3 Write model summary

Every play() invocation produces exactly **25 SID register writes** (after any
hard-restart writes for voices that just triggered a new note). The per-frame
stream is:

```
[optional gate-kill for V3, V2, V1 if pending]
V1 freq lo/hi, V2 freq lo/hi, V3 freq lo/hi   (_ct interleaved; _exe batched)
V1/V2/V3 ctrl
V1/V2/V3 AD
V1/V2/V3 SR
V1 pw lo/hi, V2 pw lo/hi, V3 pw lo/hi         (_ct interleaved; _exe batched)
filter ctrl ($D417)
volume ($D418)
filter lo ($D415)
filter hi ($D416)
```

PAL speed: 50 Hz (one play() per VBI frame). The manual confirms "one tick = 1/50
second" and "BPM is always 125 on PAL."

## 5. Instrument / Musical Model (from manual)

### 5.1 Eight graphical envelopes per instrument

CyberTracker's instrument model consists of **8 independent graphical envelopes**,
each specifying a time-value trajectory (loopable, up to 768 total envelope points
across all instruments):

| Envelope # | Name | Controls | SID output |
|---|---|---|---|
| 1 | Volume | ADSR-style but graphical | $D405/$D406 AD/SR (constrained: 16 values for A/D x-positions) |
| 2 | Waveform | wave bit selection | $D404 ctrl waveform bits (bit5=tri, bit6=saw, bit7=pulse, bit8=noise) |
| 3 | Pulse Width | $000–$FFF | $D402/$D403 PW lo/hi |
| 4 | Filter Pass | bandpass bit select | $D417 filter mode (bit0=LP, bit1=BP, bit2=HP, bit3=V3off) |
| 5 | Cutoff | filter cutoff | $D415/$D416 |
| 6 | Resonance | filter resonance | $D417 hi nibble |
| 7 | Pitch | note pitch offset | modifies $D400/$D401 freq |
| 8 | Pitch Control | pitch mode selector | controls pitch envelope behavior |

### 5.2 Envelope point structure

Points are (time, value) coordinates on a grid. Time unit = 1/50 second (1 tick).
Max instrument duration: 65,536 ticks (~21.84 minutes).

### 5.3 Vibrato and arpeggio

Separate from the 8 envelopes; per-instrument parameters.

### 5.4 Resource limits (V1.01)

- Instruments: 31 max
- Patterns: 256 max
- Pattern lines per pattern: up to 128 lines
- Total pattern memory: 796 lines
- Total track memory: 512 lines
- Total envelope points: 768

### 5.5 Speed/tempo

- Speed = ticks per pattern line (effect Fxx sets speed)
- BPM = always 125 on PAL C64 (50 Hz base)
- Speeds < 3 break the hard-restart timing
- Speed F00 = stop

## 8. _exe Executable Maker Structure

The CyberTracker Executable Maker (released 2001-12) takes a CyberTracker module
and packages it into a standalone C64 executable PRG. When this is converted to
PSID for HVSC, the result is the `CyberTracker_exe` classification.

**Standard exe layout (128/130 SIDs):**

```
$0800–$47F4:  bootstrap + envelope program handlers + main init/play framework
$47F5:        RTS (end of pre-dispatch)
$47F6–$481C:  JMP dispatch table (13 entries: JMP $49F8, $4A59, $4A6B, ... $6CB6)
$4820–$52FF:  main init and song-loader code (init at $53A2, play at $53E2)
$5300–$5530:  per-voice update subroutines
$5531–$556F:  gate/hard-restart loop (3-voice scan)
$5570–$55F5:  register write block (25 SID regs)
$5600–$6322:  song data (patterns, instruments, tracks, envelopes)
```

The init at $53A2 performs:
1. JSR $5493: copy per-voice state (initialization sweep)
2. BIT $4D00 (timing/sync read)
3. JSR $566F: voice state init
4. JSR $5531: song-loader (sets pattern/track pointers)
5. JSR $5404: clear/reset
6. JSR $62B9, $5C7C, $5F7B, $5EF2: additional subsystem inits
7. JSR $5465: final setup
8. JMP $54A7: common exit / volume init

The play at $53E2 calls the same sequence minus the one-time inits.

**Note on `$D4FF` writes in _exe**: the hard-restart uses `STA $D4FF,Y` and
`STA $D4FF` as SMC-patched placeholders. After SMC, these become `STA $D404`/
`$D40B`/`$D412` (ctrl registers). On a real C64, the SID chip responds to
$D400–$D41F; addresses $D420–$D7FF mirror the SID. $D4FF = $D4FF & $001F =
$D41F (read-only environmental register on 6581, undefined on 8580) — but
since SMC patches the address before execution, the actual write targets are
always the correct ctrl regs, not $D4FF.

## 10. Tool Handling

### sidid

`sidid` v1.x (cadaver) detects both variants via byte-pattern signatures (see §2.1).
CSDB references for the two detections:
- `CyberTracker`: https://csdb.dk/release/?id=2601
- `CyberTracker_exe`: https://csdb.dk/release/?id=6663

### libsidplayfp / VICE

Both variants are standard PSID files; no special handling needed. The _ct format
initializes cleanly to A=subtune on the JMP at $1000. The _exe format has a
bootstrap at $0800 that sets up state before the init entry at $53A2.

### DeepSID

Uses sidid engine classification for display. No CyberTracker-specific visualizer

with init=$1000 may be from the packer or from CyberTracker's native save function.

## 11. Engine Code Relocation (_ct)

The _ct engine code uses **absolute addresses** throughout and is therefore
position-dependent. CyberTracker the application relocates the engine when saving
a tune: as song data grows, all absolute address references in the engine are
adjusted by the size delta.

Verification: comparing Quasar (engine at $2014) vs Der_Fuchstanz (engine at $1FEC,
difference $28 = 40 bytes): of 512 engine bytes compared, 20 out of 21 differences
are exactly +$28 (absolute address bytes displaced by the engine position shift).
The 21st difference is a pointer into song data (also song-size-dependent).

This means: **each _ct SID binary is a unique, non-relocatable snapshot** of the
engine positioned at one specific address. There is no single "canonical" engine
binary for _ct — the engine is patched per-tune by the CyberTracker app at save time.

The _exe format avoids this problem by using a fixed layout ($0800+), with song data
at a fixed offset after a fixed-size engine.

## Leads to Follow

1. **Pattern byte encoding**: the per-voice pattern format (note byte, instrument
   byte, effect byte(s)) is not fully decoded. Binary inspection shows byte streams
   like `01 B0 FF 43 02 B0 FF...` but the exact encoding of note number, octave,
   instrument index, and effect parameters is unclear. The manual mentions
   `C- 00 0 00` display format. Binary disassembly of the pattern-reading code
   (around $20C5–$21A0) would clarify. Priority: HIGH (needed for USF extraction).

2. **Filter conflict "lowest channel wins"**: the precise mechanism (which write
   wins when multiple voices update filter on same frame) should be confirmed by
   tracing $D415/$D416/$D417 writes across a multi-voice test tune.

3. **Envelope program binary format**: the 768-point envelope pool encoding is
   uncharted. The dispatch table in _exe ($47F6–$481C) points to 8+ handlers —
   disassembling these would map the point format (lo-byte, hi-byte, loop-marker).

4. **Multi-subtune in _ct**: only 6 SIDs have 2 subtunes. The ADC #NN prefix at
   $0FFE shifts the subtune index. The subtune pointer table at $1342 is indexed
   by Y=subtune_number — verifying the exact layout (does it extend as [V1,V2,V3]
   × N_subtunes linearly?) needs a 2-subtune dissection.

5. **Pattern terminator / loop**: the track terminates at $0000, but the loop/restart
   point (the manual mentions pressing R to set a restart line) is stored somewhere
   in the song data. Find the "srep" byte in the binary.

6. **Instrument data binary format**: instrument records (31 max) contain the 8
   envelope tables plus vibrato/arpeggio parameters. Location in the song data
   region needs tracing from the pattern reader (which instrument index byte leads
   to what address in the data).

7. **_exe song data region ($5600+)**: the song data layout in _exe may differ
   from _ct. The _exe's pattern/instrument addresses are fixed (not relocatable),
   so a single _exe dissection should give the full data layout.

8. **Speed counter / CIA timing**: the `n_subtunes=1, speed=0` for all corpus
   members confirms VBI (50 Hz PAL) timing only. No CIA-timed tunes observed.
   But confirm with `siddump --writelog` on a sample to ensure the speed counter
   at $1056/$1057 doesn't produce multi-speed (the manual says "ticks per line"
   default is around 6, implying the engine runs only once per VBI = mode 1).

9. **V1.00 vs V1.01 file magic**: both versions use the same `ct` magic and $B1
   version byte. The $100D flag (01 vs 06 observed) and the meaning of the
   compressed-file change in V1.01 are unconfirmed. A side-by-side of a
   V1.00 save and V1.01 save of the same tune would clarify.

10. **The one outlier _exe**: `MUSICIANS/M/Mac_Radical/Robo-Toy.sid` has
    init=$482A (different from the $53A2 standard) — may be Executable Maker v1.00
    vs v1.01 difference. Worth comparing the $482A layout against the $53A2 layout.
