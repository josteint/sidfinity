# Basic_Program — Phase-1 local recon findings

**This file is PRIMARY ground truth derived from our own HVSC corpus + tooling.**
Research agents: READ THIS FIRST, then go gather the EXTERNAL knowledge it points
to. Do NOT re-derive these facts — extend them.

## What this category IS (established, not speculation)

- **486 SIDs**, engine label `Basic_Program` in `hvsc84.csv`. (Two adjacent
  labels are NOT this category: `Basic/Jim_Butterfield` = 47, a specific named
  player; `Basically_Music` = 12, a **machine-code** player whose name is just a
  pun — false friend, ignore both.)
- **100% RSID, version 2, `load=init=play=0`** for all 486 (verified via
  `hvsc84.csv`). This is the textbook RSID-C64-BASIC shape.
- The data region is a **tokenized Commodore BASIC V2 program** whose real load
  address (first 2 bytes of the PRG payload) is **`$0801`** — the default BASIC
  program start.
- The RSID header **flags bit 1 = "C64 BASIC flag" is SET** (decoded `0b10` on a
  sample). `HVSC/DOCUMENTS/SID_file_format.txt` (local) says: *"tunes that include
  a BASIC executable portion will be played (with the BASIC portion executed) if
  the C64 BASIC flag is set. At the same time, initAddress must be 0."* Multi-song
  BASIC tunes select the song by writing the song number to **`$030C`** before RUN.
- **The "engine" is the C64 BASIC + KERNAL ROM interpreter.** There is NO per-tune
  machine-code player and NO `play()` vector. The program runs once from RUN and
  loops via `GOTO`. Each of the 486 tunes is an independent hand-written BASIC
  program — its own micro-engine.

## How sidid classifies them (decoded from sidid.cfg `Basic_Program` entry)

The signature is tokenized-BASIC content, NOT a player fingerprint:
- `B2 35 34 32 37` = token `=` then ASCII `"5427"` → `S=54272` / `=54279` etc.
- `81 ?? B2 30 A4` = `FOR` var `=` `0` `TO`  → `FOR X=0 TO ...`
- `97 35 34 32 37` = `POKE` `"5427"` → `POKE 5427x,...`
- `B2 20 35 34 32 37` = `= 54272`

i.e. sidid flags "a tokenized BASIC program that references the SID base address
54272–54279 (`$D400-$D407`)". Confirms the category is defined by CONTENT
(BASIC that poking the SID), not by a shared engine.

## Two fully-detokenized examples (primary)

A working BASIC V2 detokenizer (token table $80–$CB, $0801 link-pointer walk) is
already proven against these files — see the recon transcript. Examples:

### `DEMOS/A-F/Ahoy_Magazine_BASIC.sid` — DATA/READ table-driven, INTERACTIVE
```
250 DIM HI(25),LO(25),DU(25),H3(64),L3(64)
260 POKE 54291,134:POKE 54277,136:POKE54284,136     <- ADSR / waveform setup
...
310 FOR X=1 TO 25:READ HI(X),LO(X):NEXT X           <- read freq hi/lo table
320 FOR X=1 TO 25:READ DU(X):NEXT X                 <- read duration table
330 FOR X=1 TO 64:READ H3(X),L3(X):NEXT X           <- voice-3 table
340 POKE 54296,15                                   <- master volume = 15
350 B=1:FOR X=1 TO 25
360 GETAN$:IFAN$=CHR$(13)THEN460                    <- INTERACTIVE: RETURN = stop
370 POKE 54272,LO(X):POKE 54273,HI(X)               <- play note X
...
420 FOR L=1 TO 145:NEXT                             <- TEMPO = busy-wait loop
430 NEXT N
440 NEXT X
450 GOTO350                                         <- loop forever
470 DATA 16,195,21,31,...                           <- the note tables
```

### `MUSICIANS/B/Bond_Alan/Two_Lines_of_Code_1_BASIC.sid` — ALGORITHMIC
```
1 S=54272:M=57272:POKES+24,15:POKES+6,255:POKES+4,81:POKES+13,255:POKES+11,23
4 POKES+1,PEEK(M)/28:POKES+8,TIANDPEEK(M+64):M=M+.2:GOTO4
```
Melody is generated by **reading ROM/RAM bytes through C64 BASIC floating-point
math** (`PEEK(M)/28`, `M=M+.2`) and the **jiffy timer `TI`**. This is the hard
sub-class: reproducing the exact writes needs bit-exact C64 BASIC FP rounding +
ROM routine behaviour.

## Provisional sub-taxonomy (to be confirmed by corpus survey)

1. **DATA/READ table-driven** (e.g. Ahoy) — note tables in DATA, FOR/NEXT delay
   for tempo. The tractable majority; close to a normal tracker once decompiled.
2. **Algorithmic** (e.g. Two Lines of Code) — notes computed from PEEK/RND/SIN/TI
   + FP math. Needs ROM-exact math to reproduce; may be nondeterministic (RND/TI).
3. **Interactive** (Ahoy has `GET`) — play-along; deterministic only if "no key"
   is the recorded path. Must confirm HVSC's recorded behaviour.

## THE TWO BLOCKERS this research must crack

### Blocker 1 — GROUND TRUTH CAPTURE (tooling)
`tools/siddump` **cannot currently run these**. By default it *skips* RSID
(`--force-rsid` needed), and even with `--force-rsid` it emits ~nothing (a single
`$D418=$0F` then silence) because **siddump.cpp never calls libsidplayfp's
`setRoms(kernal, basic, character)`** — it runs with stub ROMs, so the BASIC
interpreter can't execute the program. libsidplayfp HAS the API
(`sidplayfp::setRoms`); siddump just doesn't use it. To get ground truth we must
feed real (or redistributable open) C64 KERNAL+BASIC+CHARGEN ROM images.
→ Research cluster 5: where do legit/redistributable C64 ROM images come from
  (VICE's, the MEGA65 "OpenROMs", etc.), and how do sidplayfp/DeepSID supply them?
  (We already have `tmp/jc64/data/{basic,kernal}.rom` from another tool — provenance/licensing TBD.)

### Blocker 2 — VERIFICATION MODE (representation)
The project's two verification modes don't fit:
- Mode 1 (per-`play()` frame instruction sequence) assumes a `play()` vector firing
  once per frame. BASIC has none; writes land mid-frame at interpreter-determined
  cycles, possibly several frames apart (a `FOR L=1 TO 145:NEXT` delay) or several
  per frame.
- Mode 2 (cycle-exact) is closer but BASIC timing depends on exact interpreter
  cycle counts per statement.
The likely answer (to be validated) is a **continuous ordered `(reg,val)` write
stream** comparison (init prefix dropped, no `play()` bucketing) — and the open
DESIGN question is what the USF *content* is: decompile BASIC → note events
(principled but Turing-complete-hard for the algorithmic class) vs. lift the
ground-truth register trace into USF note events (engine-agnostic; connects to the
DEPRECATED universal register-trace fallback in `deprecated/gt2_pipeline/`).
→ This is a design decision for AFTER research; research should surface every
  relevant fact (timing model, nondeterminism risk, existing BASIC→notes tools).
